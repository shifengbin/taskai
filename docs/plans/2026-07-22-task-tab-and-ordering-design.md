# 任务标签与排序交互设计

## 目标

让用户上次选中的“未执行 / 执行中 / 已完成”标签在重启后恢复；任务条目可通过双击展开或收起终端子节点，并可在同一状态标签内拖动调整顺序。

## 方案选择

1. 仅把标签和顺序保存在前端内存：实现最少，但重启后会丢失用户选择，不满足标签记忆需求。
2. 为每个任务增加独立排序数字：可显式表达排序，但要处理跨状态转换和旧数据迁移，复杂度高。
3. 在现有任务数组中重排同状态任务，并将当前标签加入设置：保留现有 JSON 结构与原子写入能力，按状态过滤后即可得到稳定顺序。

采用方案 3。

## 数据与接口

- `Settings` 新增 `activeTaskStatus`，默认 `pending`；保存设置时校验值只能是三个任务状态之一，旧设置缺失该字段时回退默认值。
- 新增 `ReorderTasks(status, taskIDs)` 绑定。后端要求 `taskIDs` 与该状态下全部任务 ID 一一对应，再仅替换原任务数组中该状态任务所在的位置；其他状态任务和任务字段保持不变。
- 前端每次用户切换标签或状态转换后，乐观更新当前标签并异步保存完整设置；失败时恢复此前标签并提示错误。

## 任务树交互

- 双击任务条目的非按钮区域切换该任务的展开状态，单击仍只负责选中任务。
- 任务条目使用浏览器原生拖放。只能将任务放到当前标签中的另一任务上；拖放结束后调用重排绑定，再用返回的完整任务列表更新界面。
- 拖动中降低源条目透明度，并对放置目标提供轮廓提示。任务操作、状态按钮和展开按钮不会触发双击展开。

## 错误处理与验证

- 非法状态、重复 ID、缺失 ID 或混入其他状态 ID 的重排请求由后端拒绝且不写入 JSON。
- 前端排序失败时重新加载任务列表，以服务端已持久化顺序为准并显示错误。
- 测试覆盖设置默认与标签保存、后端重排与拒绝非法列表、双击展开/收起，以及拖放回调和应用持久化调用。
