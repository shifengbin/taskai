# 自动更新功能设计

## 背景

TaskAI 已有 GitHub Actions 三端发布流程，可在 tag 发布时生成 Linux DEB、Windows NSIS 安装程序和 macOS DMG。但运行中的应用没有统一的当前版本来源，也没有检查 Release、下载并校验安装包或引导安装的能力。

本次设计在任务工作台标题右侧增加紧凑的更新入口。应用启动后检查一次更新，之后每小时检查一次；检查范围包含正式版和 RC、Beta 等预发布版本。用户发现新版本后主动点击下载，下载完成后由 TaskAI 启动平台安装程序并退出。

## 目标与非目标

目标：

- 三端发布构建向应用注入统一的语义版本。
- 应用启动后及每小时检查一次 GitHub Release，包含预发布版本并忽略 Draft。
- 在“任务工作台”标题右侧显示更新状态，并由用户主动开始下载。
- 下载完成后校验文件大小和 SHA-256，成功后提示安装。
- 下载或安装程序启动失败时提供重试和手动下载。
- 安装时复用现有执行中任务退出确认，保留任务状态和工作目录。

非目标：

- 不在本次实现 Windows 代码签名或 macOS 公证。
- 不自动替换正在运行的 TaskAI 可执行文件，也不自动重启应用。
- 不为发布流程尚未提供安装包的平台或架构提供自动下载。
- 不把更新状态写入任务或设置数据。

## 方案比较

### 方案一：Go 更新服务与 Release 更新清单

发布流程生成 `taskai-update.json`，记录版本、Release 页面以及各平台安装包的名称、大小和 SHA-256。Go 后端负责版本检查、下载、校验、缓存和安装程序启动，前端只负责状态展示与用户确认。

该方案让发布产物契约集中在一个清单中，避免应用散落文件名匹配规则，跨平台行为也易于单元测试。

### 方案二：应用直接匹配 Release 资产名称

应用根据 DEB、EXE、DMG 文件名识别平台资产，再读取独立校验文件。该方案少一个清单产物，但发布文件一旦改名就可能使旧版客户端无法更新，并且平台匹配规则会进入应用代码。

### 方案三：第三方可执行文件自更新库

第三方库直接替换应用可执行文件。该方案不适合现有 DEB、NSIS 和 DMG 安装方式，也难以沿用 TaskAI 的任务退出确认语义。

采用方案一。

## 整体架构

```text
GitHub Actions
    |
    |-- 向三端应用注入当前版本
    |-- 生成 DEB / EXE / DMG
    `-- 生成 taskai-update.json
                         |
                         v
                internal/updater
    +----------------+----------------+----------------+
    | 启动及每小时检查 | 下载并校验安装包 | 启动平台安装程序 |
    +----------------+----------------+----------------+
                         |
                         | Wails 绑定与事件
                         v
        “任务工作台”标题右侧的更新状态按钮
```

新增独立的 Go 更新服务。服务持有当前版本、固定仓库地址、HTTP 客户端、缓存目录、平台信息和当前更新状态。应用启动后异步执行首次检查，再由后台计时器每小时检查一次。前端初始化时主动查询一次当前状态，并订阅后续状态事件，避免错过启动早期事件。

前端不直接访问 GitHub，也不负责写文件、计算摘要或启动进程。Wails 应用层只提供查询状态、开始下载、开始安装和打开手动下载页的入口。

## 版本发现与发布清单

GitHub 的 Latest Release 接口不返回预发布版本，因此更新服务使用 Release 列表接口，忽略 Draft，并在正式版和预发布版本中按语义版本选择高于当前版本的最高版本。无法解析为支持的语义版本时跳过该 Release，不以发布时间替代版本比较。

发布流程为所有平台向 Go 程序注入相同的当前版本。开发构建使用明确的开发版本，不从安装包文件名或 `wails.json` 反推版本。带预发布后缀的 tag 同时标记为 GitHub Prerelease，使页面元数据与版本语义一致。

每个 Release 增加以下结构的 `taskai-update.json`：

```json
{
  "schemaVersion": 1,
  "version": "0.0.0-rc6",
  "tag": "v0.0.0-rc6",
  "releaseUrl": "https://github.com/shifengbin/taskai/releases/tag/v0.0.0-rc6",
  "assets": {
    "linux-amd64": {
      "name": "taskai_0.0.0-rc6_amd64.deb",
      "size": 12345678,
      "sha256": "..."
    },
    "windows-amd64": {
      "name": "taskai-amd64-installer.exe",
      "size": 12345678,
      "sha256": "..."
    },
    "darwin-universal": {
      "name": "TaskAI-0.0.0-rc6-universal.dmg",
      "size": 12345678,
      "sha256": "..."
    }
  }
}
```

发布任务在汇总三端产物后计算文件大小与 SHA-256，再生成并上传清单。应用只接受固定仓库、当前 Release 标签和清单声明的资产名称，不执行清单提供的任意外部 URL。

当前自动更新目标为 Linux amd64、Windows amd64 和 macOS universal。运行在其他平台或架构的自行构建版本如果没有匹配资产，则不显示自动下载入口。

## 界面与状态流转

```text
无新版本
   | 检测到更高版本
   v
 [ new ] ----点击----> [ 下载中... ]
                           |
                 +---------+---------+
                 v                   v
             [ 已下载 ]          [ 下载失败 ]
                 |                   |
          弹出安装确认框       弹出下载失败对话框
                 |              |-- 重新下载
                 |              `-- 手动下载
                 v
          启动安装包并退出
```

更新入口位于“任务工作台”标题右侧、现有右侧弹性空白之前。没有新版本或自动检查失败时不显示入口，避免后台网络问题打扰正常工作。

发现更新后显示紧凑的 `new` 徽标，悬浮提示包含目标版本。点击后立即切换为固定宽度的“下载中”状态并禁止重复下载，不显示会造成头部宽度跳动的百分比。

下载成功立即弹出安装确认。用户选择“稍后”时保留已校验安装包，并把入口改为“已下载”；再次点击可重新打开安装确认。

下载失败时入口改为“下载失败”，同时显示错误对话框，提供“重新下载”“手动下载”和“取消”。手动下载打开本次目标版本对应的 GitHub Release 页面，不使用可能已经变化的通用 Latest 地址。只有用户主动下载失败才进入此状态；自动检查失败保持静默，并在下一小时继续检查。

## 下载缓存与校验

安装包和缓存元数据保存在应用数据目录下独立的 `updates/<版本>/` 目录，不写入任务或设置 JSON。每次只保留最新目标版本的已校验安装包。

下载先写入同目录的 `.part` 临时文件，同时计算 SHA-256。实际字节数与清单大小一致且 SHA-256 匹配后，才原子重命名为正式缓存文件。校验失败时删除临时文件并返回错误。

更新服务同一时刻只允许一个下载。应用启动时清理遗留的 `.part` 文件和过期版本目录；发现缓存版本不高于当前运行版本时清理该缓存。重启后必须重新计算缓存文件摘要，不能只信任之前保存的“已下载”状态。

SHA-256 用于发现下载损坏或资产不一致，不能代替代码签名和公证。签名与公证保持为后续独立变更。

## 安装与退出

```text
用户确认安装
     |
     |-- 无执行中任务 -------------------+
     |                                   |
     `-- 有执行中任务                     |
          |                              |
          v                              |
   “仍有执行中的任务”确认框                |
          | 用户确认                      |
          `------------------------------+
                                         v
                                启动平台安装程序
                                         |
                              +----------+----------+
                              | 成功                | 失败
                              v                     v
                       PrepareQuit + Quit       保持应用运行
                                               提供手动下载
```

安装流程先启动平台安装程序，成功后才调用现有 `PrepareQuit` 关闭终端并退出，避免安装程序无法启动时提前关闭当前会话。

存在执行中任务时复用现有退出确认。说明仍强调退出只关闭终端，不改变任务状态或删除工作目录；确认按钮改为“关闭终端并安装”。取消后继续保留“已下载”状态。

Windows 直接启动 NSIS 安装程序，并使用现有后台进程配置避免额外控制台窗口。macOS 使用系统 `open` 打开 DMG，Linux 使用 `xdg-open` 打开 DEB。命令均通过参数数组启动，不经 Shell 拼接路径。

安装程序启动失败时不调用 `PrepareQuit`，TaskAI 保持运行，并提供“重试安装”和“手动下载”。更新服务只负责校验和启动安装程序；应用层继续统一决定何时退出。

## 错误处理

- Release 查询失败、限流、超时或响应无效：保留当前界面，不弹提示，下个周期重试。
- Release 版本或更新清单无效：忽略该候选版本并记录错误，不下载未知资产。
- 当前平台没有匹配资产：不显示自动更新入口。
- 下载网络失败、大小不符或 SHA-256 不符：删除临时文件，显示下载失败对话框。
- 缓存重新校验失败：删除损坏缓存，恢复为可重新下载状态。
- 安装程序启动失败：应用不退出，允许重试或打开对应 Release 页面。
- 手动下载页打开失败：显示普通错误提示，不改变已经下载的缓存状态。

## 自动化测试

Go 更新服务测试覆盖：

- 正式版与 RC、Beta 的语义版本排序，忽略 Draft 和非法版本。
- 启动检查、每小时调度、检查失败后的下周期重试和停止时清理计时器。
- 平台资产选择、无匹配资产、无效清单和固定仓库边界。
- HTTP 状态错误、超时、响应中断、大小不符和 SHA-256 不符。
- `.part` 原子写入、并发下载限制、缓存重新校验和旧缓存清理。
- Windows、macOS、Linux 的安装程序启动命令及 Windows 无控制台配置。
- 无执行中任务直接安装、有执行中任务要求确认、取消后保留缓存，以及安装程序启动失败时不退出。

前端测试覆盖：

- 无更新、`new`、下载中、下载失败和已下载五种展示状态。
- 下载中禁止重复点击，失败后可重试或手动下载。
- 下载成功后立即提示安装，选择稍后可再次打开确认。
- 自动检查错误不产生下载失败提示。
- 执行中任务确认框的更新文案和取消、确认分支。
- 更新事件订阅、初始化状态读取和卸载清理。

发布脚本测试使用伪造的三端产物，验证统一版本注入、清单字段、文件大小、SHA-256、平台键和非法版本失败。修改 Wails 导出方法后运行 `wails generate module` 并检查生成绑定。

## `wails dev` 集成测试

增加仅由 `updater_integration` 构建标签启用的更新测试端点覆盖；生产构建始终使用固定的官方仓库地址。测试服务器提供比当前测试版本更高的 Release、更新清单和安装包，并让安装包第一次下载失败、第二次返回合法内容。

具体步骤：

1. 启动本地更新测试服务器，提供 `v0.0.0-rc6` Release 和对应安装包。
2. 使用以下方式启动应用，不禁用终端颜色，也不让进程自动退出：

   ```sh
   TASKAI_UPDATE_TEST_URL=http://127.0.0.1:<端口> \
   wails dev -tags updater_integration \
     -ldflags "-X main.appVersion=v0.0.0-rc5"
   ```

3. 根据 `wails dev` 输出获取调试地址，并使用 `mcp chrome-devtools` 打开。
4. 验证启动后出现 `new`，悬浮提示包含 `v0.0.0-rc6`。
5. 点击 `new`，验证入口切换为“下载中”。
6. 第一次下载失败后，验证“下载失败”入口和包含“重新下载”“手动下载”的对话框。
7. 点击“重新下载”，验证第二次下载通过大小与 SHA-256 校验并弹出安装确认。
8. 点击“稍后”，验证入口变为“已下载”；刷新页面后仍保持该状态。
9. 再次点击“已下载”，验证安装确认可以重新打开。
10. 完成浏览器验证后关闭 `wails dev` 和本地测试服务器。

集成测试使用测试构建标签替换更新源，不执行真实安装程序，也不修改生产更新地址。平台安装程序启动和退出顺序由注入启动器的 Go 测试覆盖。

## 完整验证

先运行最小相关测试，再执行：

```sh
go test -race ./...
cd frontend && npm test && npm run build
```

发布流程变更还需执行既有 Linux、Windows 和 macOS 构建脚本测试，确认版本注入没有改变原有 DEB、NSIS 和 DMG 产物。
