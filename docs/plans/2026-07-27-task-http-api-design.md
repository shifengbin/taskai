# 任务 HTTP 查询与未读动效设计

## 目标

在已有本机 HTTP 服务中提供任务列表和任务详情查询接口；HTTP 服务可由设置单独启用，而状态管理方式为 HTTP 时始终自动启用。同时为未读状态的紫色圆点增加低干扰的心跳扩散动效。

## 接口设计

复用已有 `http://127.0.0.1:<端口>/api/v1` 服务和端口，不新增第二个监听器：

- `GET /api/v1/tasks` 返回全部任务列表。
- `GET /api/v1/tasks?status=pending|running|completed` 返回对应生命周期状态的任务列表。
- `GET /api/v1/tasks/{taskId}` 返回指定任务详情。

列表和详情均返回现有任务字段：`id`、`title`、`description`、`color`、`status`、`createdAt`、`completedAt`、`workspaceRoot`、`workspacePath`。列表接口按任务存储顺序返回，不改变现有任务排序。无效 `status` 返回 JSON `400`，不存在任务返回 JSON `404`，仓储读取失败返回 JSON `500`，不支持的方法仍返回 JSON `405`。

HTTP 状态接口和任务查询接口共享服务生命周期。新增持久化设置 `httpServiceEnabled`：

- 状态管理为 `http` 时，服务无条件启动，界面的开关展示为开启且不可关闭。
- 状态管理为标题变化时，用户可通过该开关独立启动或停止任务查询服务。
- 两种启动方式共用现有 HTTP 端口；只要服务需要启动，端口必须为 `1–65535`。
- 仅独立开启服务不会向新终端注入状态上报环境变量；只有状态管理本身使用 HTTP 时才注入。

## 后端边界

`realtime.HTTPServer` 保持状态服务职责，并通过一个任务目录查询回调接收任务数据，避免让 `internal/realtime` 直接依赖任务生命周期或存储实现。应用层从现有仓储读取任务并传入该回调；因此接口始终查询持久化的完整任务信息。

`applyStatusSettings` 根据“状态管理为 HTTP 或独立服务开关开启”决定配置监听器。保存失败时沿用现有先监听、后替换、失败回滚的语义，避免关闭旧服务或写入无效设置。

## 前端展示

“实时状态”设置页将端口与 HTTP 服务开关显示在同一分区。标题变化模式下用户可切换“启用本机 HTTP 服务”；HTTP 状态模式下该开关被固定为开启，并说明由状态管理自动启用。

未读状态圆点保持紫色实心核心，并通过伪元素实现约 1.4 秒循环的透明扩散环。动效只用于 `unread`，不影响圆点的尺寸、布局或无障碍标签；在 `prefers-reduced-motion: reduce` 环境中禁用动画。

## 验证

后端测试覆盖任务列表过滤、详情查询、无效筛选、缺失任务和独立 HTTP 服务启停；设置测试覆盖端口条件和状态 HTTP 自动启用。前端测试覆盖设置联动、保存错误和未读圆点的动效标识。README 与应用内 HTTP 文档补充任务查询接口和 `curl` 示例。
