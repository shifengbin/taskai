# 任务 HTTP 终端详情设计

## 目标

在 `GET /api/v1/tasks/{taskId}` 的任务详情响应中增加当前活动终端数组。每项包含终端 ID、实际执行命令和实时状态。

## 接口契约

详情响应新增 `terminals`：

```json
{
  "terminals": [
    {"id": "terminal-1", "command": "/bin/zsh", "status": "working"},
    {"id": "terminal-2", "command": "codex", "status": "idle"}
  ]
}
```

- 普通终端的 `command` 为其实际使用的 Shell 路径。
- 自定义命令终端的 `command` 为启动时传入的命令，不拼接参数。
- `status` 使用已有实时状态值：`idle`、`working`、`unread`、`error`。
- 仅返回仍由终端管理器持有的活动会话；没有活动终端时返回空数组 `[]`。
- `GET /api/v1/tasks` 保持既有结构，不返回 `terminals`。

## 数据流

终端管理器在创建会话时已取得 Shell、命令和终端 ID，但此前只保存了基本 `Info`。增加一个只读活动会话快照方法，按终端 ID 稳定排序返回 ID 和有效命令：无显式命令时使用 Shell 路径。应用层在查询详情时读取该快照，并逐项向实时服务查询状态，再映射到 HTTP 资源。

终端状态和会话均为内存态，不写入任务 JSON。任务完成、应用重启或终端退出后不会在接口中返回历史终端，这与当前终端生命周期一致。

## 验证

应用层 HTTP 回归测试使用可控终端后端创建一个普通 Shell 终端和一个自定义命令终端，设置不同实时状态后请求详情。测试断言详情返回两项且字段类型和值正确，并断言任务列表仍没有 `terminals` 字段。终端管理器测试覆盖有效命令的选择与活动会话快照。
