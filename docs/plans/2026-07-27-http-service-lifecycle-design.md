# HTTP 服务生命周期与命令环境设计

## 目标

修正保存无关设置（例如切换任务标签）时重复监听 HTTP 端口的问题；让任务上下文环境变量覆盖所有命令启动路径；补全 HTTP 文档中的合法参数说明；让工作中状态点与未读状态点均具有扩散动画。

## HTTP 服务生命周期

应用启动时继续按当前设置启动或关闭 HTTP 服务。后续保存设置时，只在下列字段变化时才处理 HTTP 监听器：

- `httpServiceEnabled`
- `statusManagementMode`
- `statusManagementHTTPPort`

其他设置（包括 `activeTaskStatus`）不触碰监听器。HTTP 状态模式和独立 HTTP 服务开关共同决定服务是否运行；两者均不启用时关闭服务。状态管理方式变化但服务仍运行且端口相同，只更新实时状态模式，不重启 HTTP 监听器。

`HTTPServer.Configure` 同时保持幂等：同一个已监听的固定端口再次配置时直接成功返回。这样即使未来新增调用点，也不会因重复 `net.Listen` 报端口被占用。

## 环境变量规则

| 启动路径 | `TASKAI_TASK_ID` | `TASKAI_TERMINAL_ID` | `TASKAI_STATUS_API` |
| --- | --- | --- | --- |
| 普通终端、显示终端的自定义命令 | 始终注入 | 始终注入 | 仅 HTTP 状态管理模式注入 |
| 无终端后台自定义命令 | 始终注入 | 不注入 | 不注入 |
| 前置、后置脚本 | 始终注入 | 不注入 | 不注入 |

后台命令和脚本没有可上报状态的终端实体，因此仅暴露任务 ID。调用进程仍保持现有任务工作目录和已选择 Shell。

## 文档与动效

HTTP 说明弹窗把两个 `status` 的合法值明确分开：

- `GET /api/v1/tasks` 的查询参数 `status` 可省略，或为 `pending`、`running`、`completed`。
- 两个 `PUT` 状态更新接口的 JSON 字段 `status` 必填，且只能为 `idle`、`working`、`unread`、`error`。

“working”和“unread”状态点共用扩散动画节奏，以各自绿色、紫色扩散环区分；空闲与异常保持静态。系统要求减少动态效果时禁用两者动画。

## 验证

后端测试覆盖同端口重配、保存非 HTTP 设置时保持监听器和所有命令路径的环境变量。前端测试覆盖文档合法参数文本以及工作中状态点的动效标识。最后执行竞态测试、完整前端测试、项目构建脚本和差异检查。
