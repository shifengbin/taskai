## Context

TaskAI 已有由 `add-build-release-workflow` 建立的三端发布链路，可生成 Linux amd64 DEB、Windows amd64 NSIS 安装程序和 macOS universal DMG，并将产物挂载到 GitHub Release。运行中的应用目前没有可靠的自身版本来源，也没有 Release 查询、安装包下载校验、持久缓存和安装引导能力。

该变更同时涉及 GitHub Actions、三端构建脚本、Go 后端、Wails 生命周期与绑定、React 任务工作台头部，因此需要先固定发布端与客户端之间的契约。更新功能必须保持现有任务数据、工作目录和终端退出语义；自动检查失败不得打断正常工作；生产构建不得允许任意更新源覆盖。

主要参与者包括使用已发布桌面安装包的 TaskAI 用户、维护发布流程的开发者，以及通过 `wails dev` 验证完整交互的测试人员。

## Goals / Non-Goals

**Goals:**

- 为三端发布构建注入统一、可比较的当前应用版本。
- 启动后检查一次更新，之后每小时检查一次，候选范围包含正式版和预发布版本并排除 Draft。
- 在“任务工作台”标题右侧提供紧凑、稳定的更新状态入口，由用户主动开始下载。
- 通过 Release 清单选择当前平台安装包，并在下载完成后校验大小和 SHA-256。
- 将已校验安装包保存到独立更新缓存，并在重启后重新校验恢复。
- 下载或安装程序启动失败时保留应用可用性，并提供重试及目标 Release 页面的手动下载入口。
- 安装时复用现有执行中任务确认和 `PrepareQuit` 语义，仅在平台安装程序成功启动后关闭终端并退出。
- 提供不接触真实 GitHub Release 和真实安装程序的 `wails dev` 集成测试路径。

**Non-Goals:**

- 不在本变更中加入 Windows 代码签名、macOS 签名或公证。
- 不直接替换正在运行的 TaskAI 可执行文件，也不自动重启应用。
- 不为发布流程没有提供安装包的平台或架构实现自动下载。
- 不在任务或设置 JSON 中保存更新状态。
- 不在生产构建中暴露环境变量、命令行参数或设置项来替换官方更新源。

## Decisions

### 1. 使用独立 Go 更新服务和 Release 清单

新增 `internal/updater`，由其负责版本发现、状态机、下载、校验、缓存恢复和平台安装程序启动。前端只读取状态、发起明确的用户操作并展示确认；不直接访问 GitHub、不写安装包，也不计算摘要。

每个 GitHub Release 附带 `taskai-update.json`：

```json
{
  "schemaVersion": 1,
  "version": "0.0.0-rc6",
  "tag": "v0.0.0-rc6",
  "releaseUrl": "https://github.com/shifengbin/taskai/releases/tag/v0.0.0-rc6",
  "assets": {
    "linux-amd64": {
      "name": "taskai_0.0.0-rc6_amd64.deb",
      "size": 12345678,
      "sha256": "..."
    },
    "windows-amd64": {
      "name": "taskai-amd64-installer.exe",
      "size": 12345678,
      "sha256": "..."
    },
    "darwin-universal": {
      "name": "TaskAI-0.0.0-rc6-universal.dmg",
      "size": 12345678,
      "sha256": "..."
    }
  }
}
```

发布任务汇总三端产物后计算大小和 SHA-256，再生成并上传清单。更新服务只接受官方 `shifengbin/taskai` 仓库中同一 Release 的清单和资产：清单 tag、version、Release 页面必须与 GitHub API 响应一致，安装包名称必须在同一 Release 的资产集合中，不能把清单中的任意 URL 当作下载源。

选择该方案是因为安装包命名、平台映射和摘要契约集中且可版本化，旧客户端不会因后续文件名变化而依赖猜测规则。直接按文件名匹配 Release 资产更简单，但会把脆弱的命名规则固化在客户端；直接替换可执行文件的第三方更新库也不符合 DEB、NSIS、DMG 的现有安装模型。

### 2. 使用语义版本比较并包含预发布版本

更新服务调用 GitHub Releases 列表接口，而不是只返回正式版的 Latest Release 接口。它忽略 Draft、无效语义版本、版本不高于当前应用及无当前平台资产的条目，从剩余条目中选择语义版本最高者。比较时将 tag 和注入版本规范化为带 `v` 前缀的语义版本；预发布优先级遵循语义版本规则，不以发布时间代替版本顺序。

三端构建脚本继续接收发布工作流解析出的统一版本，并通过 Go linker flag 写入 `main.appVersion`。发布构建必须嵌入与 tag 等价的版本，开发构建使用明确的开发版本。带预发布后缀的 tag 创建的 GitHub Release 同时标记为 Prerelease。

采用标准语义版本规则可正确处理 `rc`、`beta` 和正式版之间的顺序。按发布时间选择会在补发旧版本或编辑 Release 时产生错误更新目标。

### 3. 后端维护单一更新状态，前端通过查询加事件同步

更新状态使用有限状态机表达：`idle`、`available`、`downloading`、`downloaded`、`download_failed`。状态携带目标版本和 Release 页面；需要时携带可展示的错误信息，但自动检查错误不进入 `download_failed`。

应用启动完成后异步执行首次检查，随后由一个可停止的小时计时器调度检查。应用关闭时取消请求并停止计时器。同一时刻只允许一次检查和一次下载，下载中的重复请求直接复用当前状态而不创建第二个写入者。

Wails 应用层导出状态查询、开始下载、启动已下载安装包和打开手动下载页等窄接口，并发布 `updater:state-changed` 事件。前端挂载时先查询当前状态，再订阅后续事件，避免启动检查早于 React 订阅造成状态丢失；卸载时清理订阅。

没有更新和自动检查失败时头部不显示入口。发现更新后显示固定尺寸的 `new` 标记；用户点击后显示下载中，成功后显示已下载，失败后显示下载失败。下载中不显示百分比，避免标题栏宽度随进度变化。

### 4. 下载采用临时文件、流式校验和持久缓存

更新缓存位于应用数据目录下独立的 `updates/<version>/`，不修改 `tasks.json` 或设置结构。安装包先写入同目录 `.part` 文件，写入过程中计算 SHA-256；只有实际字节数和摘要都与清单一致时，才原子重命名为最终文件。失败或取消时删除临时文件。

启动恢复会删除遗留 `.part`、当前版本及更旧版本的目录和非当前候选缓存。恢复 `downloaded` 状态前必须重新读取文件并核对大小和 SHA-256，不能只信任元数据。正常情况下仅保留最高目标版本的有效安装包。

该设计支持断电或进程终止后的安全恢复，并避免把半成品当作安装包。代价是每次重启会重新读取一次缓存文件，但安装包大小可控，且完整性优先于启动时少量 I/O。

### 5. 安装程序先启动，随后复用现有退出流程

平台启动器使用参数数组直接创建进程，不经过 Shell 拼接路径：Windows 启动 NSIS `.exe`，并复用后台进程配置避免出现额外控制台窗口；macOS 执行 `open <dmg>`；Linux 执行 `xdg-open <deb>`。

用户选择安装时，前端先检查执行中任务。存在执行中任务则复用“仍有执行中的任务”确认框，正文继续说明只关闭终端、不改变任务状态、不删除工作目录，确认动作显示“关闭终端并安装”。取消后维持 `downloaded` 状态。

确认安装后先调用后端启动器。只有启动器返回成功，前端才依次调用现有 `PrepareQuit` 和 Wails `Quit`。启动失败时不调用 `PrepareQuit`，应用继续运行并提供重试安装和手动下载。这个顺序保证安装程序无法启动时不会提前丢失当前终端会话。

不采用应用自身替换二进制，是因为包管理器和平台安装器需要继续负责权限、安装布局及卸载元数据。

### 6. 测试源覆盖只存在于专用构建标签

生产实现将 GitHub API 根地址和官方仓库固定在代码中。使用 `updater_integration` 构建标签时，由替代文件允许从 `TASKAI_UPDATE_TEST_URL` 读取本地测试服务地址，并注入不执行真实平台安装的测试启动器；未带该标签的构建既不读取该变量，也不暴露更新源设置。

本地测试服务器模拟 Releases 列表、清单和安装包，第一次安装包请求返回失败，第二次返回具有正确大小和 SHA-256 的内容。这样可在 `wails dev` 中验证完整 UI 状态流转，而不会依赖 GitHub 网络、污染真实 Release 或启动系统安装程序。

相比在生产代码中提供通用 URL 覆盖，此方案多维护少量 build-tag 文件，但显著缩小了供应链攻击面。

## Risks / Trade-offs

- [未签名安装包会触发系统安全提示] -> Release 继续明确首次运行步骤，本变更不把 SHA-256 描述成来源认证；签名与公证作为独立后续变更。
- [GitHub API 限流、离线或暂时故障] -> 启动检查和每小时检查均设置超时，失败保持静默并等待下个周期；用户主动下载失败时才展示错误。
- [清单与 Release 资产不一致] -> 严格校验 schema、tag、version、Release 页面、平台键、文件名、大小和 SHA-256，不一致则忽略候选版本。
- [下载过程中应用退出会留下半成品] -> 仅写 `.part`，启动时统一清理，正式缓存只由成功校验后的原子重命名产生。
- [安装程序启动成功不等于用户完成安装] -> TaskAI 只承诺把控制权交给平台安装器；用户取消安装后可继续从现有版本启动应用。
- [先启动安装程序、后关闭终端时 `PrepareQuit` 可能失败] -> 此时不调用 `Quit` 并向用户显示错误，避免强制退出；已启动的安装程序由用户决定是否继续。
- [每小时检查可能在睡眠恢复后集中触发] -> 使用单一串行检查锁，任何时刻最多一个检查请求，不补跑错过的周期。
- [当前发布工作流变更尚未归档] -> 实施时基于 `add-build-release-workflow` 的最终工作流扩展，不另建竞争的发布流程；若其接口变化，先同步本设计中的产物名与平台键。

## Migration Plan

1. 在功能 worktree 中先完成发布版本注入与清单生成测试，再实现更新服务及前端状态入口。
2. 生成新的 Wails 绑定并运行 Go、前端和发布脚本测试。
3. 使用 `updater_integration` 标签启动本地测试服务和 `wails dev`，通过浏览器验证从 `new` 到首次失败、重试成功、稍后安装及缓存恢复的完整流程，然后关闭调试进程。
4. 构建并打开当前平台可执行程序，等待人工确认后才将 worktree 分支合并回当前工作区分支。
5. 合并后重新执行完整测试与构建，随后同步 README/OpenSpec 文档、归档已完成变更、提交并移除 worktree。

回滚时可以移除任务工作台更新入口和更新服务启动，不影响任务数据；独立 `updates/` 缓存可以安全忽略或清理。发布端应同时停止生成新 schema 清单，旧客户端在无有效清单时保持静默，不阻止应用启动。

无。当前产品行为、支持平台、检查频率、预发布策略、失败降级、缓存恢复和安装退出顺序均已确认。
