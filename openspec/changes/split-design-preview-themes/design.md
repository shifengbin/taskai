## Context

`taskai/design-preview/index.html` 是一个不经过 Vite 或 Wails 构建的静态设计目录。它在同一份 HTML 中维护了 gallery 外壳、36 套主题 CSS、36 个主题说明区块，以及通过 `appHTML()` 注入到每个主题中的任务工作台骨架。每套主题包含亮色和暗色两个变体，主题之间共享任务、终端和状态语义，只改变视觉令牌和组件皮肤。

本变更的参与者主要是需要浏览设计方向的产品/设计人员，以及后续把选定主题落地到 React + MUI 的开发人员。约束包括：文档使用中文；页面必须保持静态文件属性；现有任务、终端和应用运行时不应受到影响；页面应能直接从文件系统打开，而不要求启动开发服务器。

## Goals / Non-Goals

**Goals:**

- 将 36 套主题按稳定编号和 kebab-case 名称拆到 `design-preview/themes/<number>-<slug>/`。
- 每个主题目录提供 `index.html` 和中文 `design.md`，页面展示该主题的亮色和暗色预览。
- 让主题页面复用同一份预览骨架、图标符号、终端输出示例和基础布局规则。
- 保持现有主题 CSS 令牌、主题专属品牌文案、任务/终端状态和预览交互语义不变。
- 将根目录 `index.html` 变成覆盖全部 36 套主题的总览入口，并为每个主题提供可验证的相对链接。
- 让每份设计文档能够作为后续 React + MUI 视觉实现的依据，而不需要重新阅读单体 HTML。

**Non-Goals:**

- 不修改 `frontend/src/`、Go 代码、Wails 绑定、业务 API、任务状态或终端行为。
- 不在本变更中把任何主题落地到实际应用，也不选择最终生产主题。
- 不引入新的运行时依赖、字体 CDN 方案或服务端路由。
- 不把静态设计预览改造成完整的主题切换应用；总览页只负责导航，主题页只负责展示自己的主题。

## Decisions

### 目录与命名

采用固定编号加小写短名的目录名，例如 `01-monolith`、`02-atelier`、`36-pixel`。每个目录至少包含：

```text
themes/01-monolith/
├── index.html
└── design.md
```

公共文件放在 `design-preview/_shared/`，包括基础 gallery 样式、预览骨架脚本、SVG 图标符号和终端示例内容。根目录 `index.html` 保留为总览页，链接到 `themes/*/index.html`，不再内嵌全部主题页面。

选择这种结构是因为主题页面仍然是清晰的独立交付单元，同时公共结构只维护一份。每个页面使用相对路径引用 `_shared` 资源，因此直接打开仓库内的 `index.html` 或主题页不需要 HTTP 服务。完全把公共 CSS 和脚本复制到 36 个页面的方案虽然可以单独复制目录运行，但会让基础结构修复和无障碍修复产生 36 份重复维护，暂不采用。

### 页面渲染模型

每个主题页面保留两个 `.mockup` 实例，分别带有 `light` 和 `dark` 标识，并使用同一份 `appHTML()` 结构生成任务工作台。公共脚本通过页面上的主题配置或主题类名设置品牌名、窗口标题和少量主题专属装饰，不再在一个页面中遍历 36 个主题的条件分支。

页面必须继续支持当前静态预览已有的行为：

- 亮/暗预览并排展示，并在小屏幕上横向滚动。
- 工作中和未读状态点保留脉冲表现，并尊重 `prefers-reduced-motion`。
- 主题选择按钮只在主题页内更新选择提示，不触发应用运行时逻辑。
- 页面可通过可选的查询参数隐藏总览外壳，以便截图单个主题。

### 主题样式提取

从现有单体文件按主题注释边界提取 `.d-*` CSS 区块和对应的亮/暗令牌，不重新设计颜色或组件尺寸。公共样式保留 `.stage`、`.app`、`.sidebar`、`.pane`、`.term-body` 等结构规则；主题样式只覆盖自己的变量、字体、边框、阴影、状态色和装饰。

19–24 号主题的 hard-shadow 规则以及 25–36 号主题的 Pop family 规则可以在公共文件中抽取真正稳定的家族基础，但最终页面必须保留每套主题可追溯的变量定义和差异覆盖，避免文档无法解释单个主题的实际效果。

### 设计文档格式

每套 `design.md` 使用统一章节，内容从现有主题区块和 CSS 令牌整理而来：

1. 主题定位、目标场景和设计关键词。
2. 视觉原则与亮/暗模式的差异。
3. 色彩 Token 表，至少包含画布、表面、正文、辅助文字、边框、强调色、工作中、空闲、未读和异常色。
4. 字体、字重、字号、大小写和等宽终端字体规则。
5. 布局与组件规则，覆盖顶栏、品牌标记、侧边栏、标签页、任务项、终端标签和终端输出区。
6. 状态、悬停、选择、脉冲、减少动态效果等反馈规则。
7. 可读性和无障碍注意事项。
8. 从预览类名/变量到 React + MUI 实现的映射建议。

### 生成与维护方式

使用一次性或可重复运行的 Node.js 提取脚本完成机械拆分：读取现有 `index.html` 的主题 CSS、主题元数据和公共模板，生成 36 个主题页面的初始文件。设计文档由统一模板生成骨架后逐主题补齐，不把文档内容隐藏在运行时脚本中。若保留脚本，脚本只生成静态预览资产，不接入 TaskAI 编译流程；页面和文档本身仍是提交到仓库的事实来源。

### 验证方式

验证分为结构检查和浏览器检查：

- 结构检查确认主题目录数量为 36，每个目录都存在 `index.html` 和 `design.md`，每个主题页面同时包含 light/dark 变体。
- 链接检查确认总览页的 36 个链接均指向存在的相对路径，主题编号、名称和页面标题一致。
- 浏览器检查随机覆盖早期独立主题、hard-shadow 家族和 Pop family 主题，确认页面直接打开不报资源错误、无空白 stage、亮暗变体可见、终端输出可读。
- 运行 `design-preview` 相关的静态检查后，再按项目要求执行前端构建；本变更不需要 Go 测试或 Wails 绑定生成。

## Risks / Trade-offs

- [公共资源相对路径错误] → 所有主题页都使用固定的 `../../_shared/` 相对路径，并在结构检查中验证脚本、样式和图标资源存在；额外覆盖直接用浏览器打开文件的场景。
- [拆分后主题样式串入其他主题] → 每个主题页面只加载自己的主题 CSS，公共 CSS 不包含主题变量；使用主题类名前缀检查重复和未定义变量。
- [36 份设计文档内容不一致] → 使用统一章节模板和主题清单逐项验收，要求每份文档至少覆盖色板、字体、布局、组件、状态和实现映射。
- [根目录总览遗漏主题] → 从同一份主题清单生成导航，并用脚本比较目录、页面标题、总览链接和文档标题的集合。
- [外部 Google Fonts 在离线环境不可用] → 保持当前预览的字体回退链，并在文档中明确外部字体依赖；本变更不把 CDN 字体改造成应用运行时依赖，也不改变生产应用字体方案。
- [共享资源降低单目录可复制性] → 文档明确主题页依赖 `_shared`，验收目标是仓库内直接打开而不是把单个主题目录复制到仓库外独立运行；如后续需要独立打包，可再增加静态内联构建步骤。

## Migration Plan

1. 在 worktree 中创建公共资源目录和 36 个主题目录，先从现有单体文件提取页面和文档草稿。
2. 校验每个主题页与原主题区块的亮暗渲染和状态语义一致。
3. 将根目录页面改为总览入口，并确认 36 个相对链接全部有效。
4. 运行静态结构检查和浏览器抽样检查；失败时只回滚本变更目录及 `design-preview` 文件，不涉及应用运行时代码。
5. 合并并按项目要求执行编译验证。

回滚方式是恢复原 `design-preview/index.html` 和 `readme.md`，删除新增主题目录及 `_shared` 目录；由于不改变运行时代码，不需要数据迁移或 API 回滚。

## Open Questions

- 是否要求把单个主题目录复制到仓库外后仍能独立运行；当前设计按“仓库内直接打开”处理。
- 是否需要把 Google Fonts 下载并改为本地字体资源；这会扩大静态资源体积和版权/许可核查范围，当前不纳入本变更。
