## Context

额外信息管理中的新增和编辑信息弹窗会把固定字段直接写回 `extraInfoDraft.fields`。内置 Git 模板的固定字段为 `name`（项目名称）和 `repository`（仓库地址），但两者目前互不关联。项目名称既作为信息展示名称，也会被后续 Git 克隆生命周期命令用于目标目录，因此仓库地址与名称不一致会增加用户修正成本。

本变更仅影响前端草稿状态。已保存的信息、后端 API、数据模型和任务快照均继续使用既有字段结构。

## Goals / Non-Goals

**Goals:**

- 在用户编辑 Git 信息的仓库地址时，自动从有效 Git 地址回填空的项目名称。
- 不覆盖任何非空项目名称，保留用户的手工命名权。
- 使用可预测且与需求示例一致的提取规则，并以交互测试防止回归。

**Non-Goals:**

- 不解析或校验仓库地址是否可连接，也不支持从不含 `.git` 后缀的地址推断名称。
- 不在选择模板、加载默认值、加载既有信息或保存时补写项目名称。
- 不追踪“自动生成”名称的来源；回填后该名称与手工名称同样受保护。
- 不改变非 `git` 分类，或任务编辑器中的只读 Git 信息快照。

## Decisions

### 1. 在固定字段输入事件中完成回填

仓库地址和项目名称只在额外信息编辑草稿中同时可编辑，因此在 `repository` 文本框的更新逻辑中同步更新两个字段。触发条件使用稳定字段键和分类值：仅当草稿 `catalogue` 为 `git` 且被编辑字段键为 `repository` 时执行；不依据可配置的显示名称判断。

另一种方案是在表单层监听整个草稿的变化并通过 effect 回填。该方案会在默认值初始化、编辑旧信息或其他状态更新时产生隐式写入，无法满足“填写地址时”的边界，因此不采用。

### 2. 采用严格、最小的字符串提取规则

提取函数先去除地址首尾空白，再要求其以 `.git` 结束；从最后一个 `/` 后取出 `.git` 前的非空片段。该规则同时覆盖 HTTPS URL 和 `git@gitlab.jiandan100.cn:webdev/interact-study.git` 形式的 SSH 地址，并与需求中的“最后一个 `/` 之后到 `.git` 之前”完全一致。

不使用 URL 解析器：SCP 风格的 SSH 地址不是标准 URL，仍需额外分支；对当前确定的规则，独立的小型纯函数更直接且易测试。无最后路径段、无 `.git` 后缀或名称为空时返回空结果，调用方保持名称不变。

### 3. 仅保护非空项目名称，不记录来源

更新仓库地址时，先保留输入的原始仓库地址值；只有当前 `name` 经 `trim()` 后为空且提取成功，才把项目名称设为提取值。已填名称，包括此前自动生成的名称，都不因后续地址编辑而变化。用户若希望根据新地址重新提取，可先清空项目名称再编辑地址。

记录“自动生成”来源并在地址变化时持续同步是另一种方案，但会让用户难以判断何时名称会被覆盖，且超出“已有名称不修改”的明确要求。

## Risks / Trade-offs

- [用户输入未以 `.git` 结尾的有效仓库地址] → 不自动回填，用户仍可手工填写名称；规则与需求的 `.git` 边界保持一致。
- [用户先填入一个地址，之后改为另一个地址] → 首次回填的名称不会随之变化；这是保护已有名称的既定语义，用户可显式清空后重新触发。
- [非 Git 模板也定义 `repository` 字段] → 同时检查 `catalogue === 'git'`，避免跨分类副作用。

## Migration Plan

1. 在前端草稿更新逻辑中加入提取与条件回填。
2. 增加前端交互测试，覆盖成功回填、已有名称保护和非 Git 分类。
3. 发布后仅影响用户此后的字段编辑；既有数据无需迁移，回滚只会停止新的自动回填。
