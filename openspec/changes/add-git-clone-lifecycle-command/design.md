## Context

当前生命周期命令链只以有序 `commandIds` 引用全局命令。自定义命令的参数属于全局命令定义，因而同一个命令在不同链中不能具有不同运行参数。系统内置目录命令不会调用外部程序；任务已保存的内置 Git 信息快照则已稳定地保存项目名称、仓库地址和可选仓库分支，但尚未被生命周期运行器使用。

本变更需要在不改变首命令 JSON 上下文和命令标准输入输出传递规则的前提下，增加链级参数和一个安全、可重试的 Git 批量克隆内置命令。现有命令链实现尚在工作区中未提交，本设计以其已经确立的“全局命令 + 命令链 + 任务引用”模型为基础。

## Goals / Non-Goals

**Goals:**

- 让命令链为每次命令引用保存参数，并按“命令固有参数在前、链级参数在后”的顺序合并后执行。
- 提供固定 ID、不可编辑和不可删除的 Git 仓库克隆系统命令，并只读取任务选择的内置 Git 信息快照。
- 在 `beforeStart`、`beforeEnd` 和 `updateTask` 中安全、顺序、可重试地批量克隆仓库。
- 让系统命令携带机器可读的参数说明，命令库和链编辑器都能展示该说明。
- 无损迁移已有 `commandIds` 命令链数据。

**Non-Goals:**

- 不修改 Git 信息模板、任务详情 HTTP 的 `extraInfo` 结构，或新增 Git 信息编辑字段。
- 不自动把 Git 命令加入默认链；用户自行将它放在需要的命令链，并决定其相对于创建目录命令的顺序。
- 不执行拉取、合并、推送、删除仓库、处理子模块或管理 Git 凭据。
- 不支持每个仓库单独指定克隆目录，也不在一次运行中并行克隆。

## Decisions

### 1. 用带参数的链命令引用替代裸命令 ID

为链内条目定义 `LifecycleCommandReference`，包含 `commandId` 和 `arguments`。`LifecycleCommandChain` 保存有序 `commands`，不再以平行数组或参数映射关联命令和参数。运行器解析引用后计算：

```text
有效参数 = 全局 LifecycleCommand.arguments + LifecycleCommandReference.arguments
```

全局命令仍负责可复用的默认参数，链级参数仅影响当前链；复制命令链时深拷贝各引用及参数。参数按既有规则去除空白项但保留顺序。自定义命令接收合并后的全部参数，系统命令也从同一参数列表解析自己的配置。

选择该模型而非在 `LifecycleCommand` 上保存 `dir`，是因为全局 Git 命令不能同时满足不同链的目录需求。也不使用 `map[commandID][]string`，以免未来允许同一命令在同一链重复出现时发生冲突。

加载旧设置时，若只存在 `commandIds`，按原顺序转换为参数为空的引用；保存后仅写入新结构。所有删除约束、适用钩子覆盖校验和任务链选择都改为遍历引用的 `commandId`。

### 2. Git 命令使用固定参数语法和静态参数文档

新增固定命令 ID `system.lifecycle.git-clone`、类型 `git-clone`、名称“Git 仓库克隆”，适用范围固定为 `beforeStart`、`beforeEnd`、`updateTask`。固定命令规范化时始终恢复其类型、名称、适用范围和参数说明，因此用户不能篡改、编辑或删除它。

Git 链级参数采用单行 `dir=<相对目录>` 语法，且必须恰好出现一次；未知、重复、空值、绝对路径和越出任务工作目录的路径均在保存命令链时被拒绝。`dir=.` 表示任务工作目录本身。该语法作为合并后的一个入参保留，使系统命令与自定义命令共享统一的链级参数传递机制。

`LifecycleCommand` 为系统命令携带只读参数说明（键、是否必填、用法和描述）。命令库在系统命令概要之后显示说明；链编辑器在该命令的链级参数输入旁显示同一说明。采用后端固定定义而非仅前端硬编码，确保 API 客户端和后续系统命令共享唯一文档来源。

### 3. Git 克隆只消费内置 Git 信息并保证目标目录安全

运行器从当前任务的额外信息快照中筛选内置 Git 模板 ID 的条目，而非仅按 `catalogue` 名称匹配。每条条目读取固定字段 `name`、`repository` 和动态参数 `branch`；没有 Git 条目时命令成功返回原始标准输入。

对每个条目，先校验项目名称是安全的单个目录名、仓库地址非空，再将 `dir` 解析为任务工作目录下的克隆根目录，目标为 `<任务工作目录>/<dir>/<项目名称>`。命令会创建不存在的克隆根目录；若目标已经存在，不检查其内容、不访问远程且直接跳过，以避免覆盖用户文件并使重试幂等。目标是普通文件或目录时都视为已存在并跳过。

链中的创建任务工作目录命令仍由用户排序控制。Git 命令自行创建其 `dir` 根目录，但不会在任务工作目录本身不存在时绕过任务工作区边界；因此常规 `beforeStart` 链应将“创建任务工作目录”排在 Git 命令之前。

### 4. 用直接的 Git 子进程调用实现分支选择与失败语义

Git 系统命令不经用户选定的 Shell 执行；运行器使用参数化子进程调用 `git`，避免仓库地址、分支和目录值被 Shell 解释。每个项目依次执行：

1. 分支为空时直接 `git clone`，由远程默认分支完成初始检出。
2. 分支非空时，以 `git ls-remote --exit-code --heads` 检查远程同名分支；存在则 `git clone --branch` 该分支。
3. 检查结果表明远程分支不存在时，先普通克隆远程默认分支，再基于当前 `HEAD` 创建指定名称的本地分支。

无法找到 `git`、认证/网络失败、无效分支、克隆失败或本地分支创建失败均终止当前 Git 命令和整条生命周期链。先前成功的项目已占用目标目录，重试时会被跳过，失败项目和后续项目可继续处理。Git 子进程的标准输出不替换链上下文；系统命令成功后原样传递输入字节，与既有目录内置命令一致。

选择远程默认分支而非硬编码 `main`，可兼容仍使用 `master` 或其他默认分支的远程仓库。选择失败即停止而非收集所有失败，是为了保留既有链的失败语义和可重试性。

## Risks / Trade-offs

- [私有仓库认证需要交互] → 沿用用户本机 Git 凭据、SSH 代理和凭据管理器；命令失败时保留 Git 标准错误供生命周期错误展示。
- [远程状态在分支检查后变化] → Git 克隆的实际错误终止本轮；已存在目录跳过使修复后重试不会重复克隆成功项目。
- [项目名称相同导致目标冲突] → 第一个成功项目创建目录，后续同名项目按已存在规则跳过；文档明确目标由项目名称决定。
- [迁移改变持久化 JSON 形状] → 仅在加载时从旧字段构造新引用，且迁移测试覆盖顺序、空参数与既有任务链引用。
- [Git 被放在没有创建工作区的开始前链中] → 命令提示任务工作目录不存在；界面文档说明常规排序要求，不隐式创建任务工作目录。

## Migration Plan

1. 增加链命令引用和 Git 系统命令类型，保持旧 `commandIds` 的反序列化兼容。
2. 加载设置时把旧 ID 列表按原顺序迁移为参数为空的引用；重新持久化为新结构并补齐 Git 固定命令。
3. 更新 Wails 绑定、前端类型和链编辑界面后，运行 Go、前端测试及项目 `scripts` 构建脚本。
4. 回滚到旧二进制时，旧版本可忽略新增字段；已迁移的链不会丢失原有命令顺序，但不会使用链级参数或 Git 命令。

## Open Questions
