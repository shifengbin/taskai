## Context

任务 Git 标签当前通过 `internal/repositorygit` 递归遍历任务工作目录，并在每个目录执行 `git rev-parse --show-toplevel`。Windows GUI 应用直接启动这些 Git 控制台进程时没有应用项目已有的后台无窗口属性，所以一次扫描会按目录数量连续弹出黑框。发现仓库后，服务还会执行状态和远程查询；任一仓库的基础状态读取失败会使整个列表请求失败。

扫描深度与默认目录布局也不一致：深度定义以任务目录为第 1 层、直属子目录为第 2 层，但内置 `iterations-ai` 和“更新仓库”链将批量仓库放在 `workspaces/<项目>`，仓库本身处于第 3 层。当前默认深度为 2，因此默认生命周期创建的仓库可能无法被默认 Git 扫描发现。

项目已经在生命周期命令链和任务菜单后台命令中使用同一套 Windows 无控制台窗口属性。此次变更需要让任务 Git 服务复用相同策略，同时保持内嵌终端、Git 输出、错误和退出状态不变。仓库路径仍必须受任务工作目录真实路径边界保护。

## Goals / Non-Goals

**Goals:**

- Windows 上打开 Git 标签或执行仓库操作时不显示 TaskAI 直接启动的 Git 控制台窗口。
- 默认设置能够发现默认生命周期创建在 `workspaces/<项目>` 中的仓库。
- 仅对具有 `.git` 目录或文件的候选目录执行 Git 验证，减少扫描产生的子进程数量。
- 单个无效候选或仓库状态读取失败时，继续返回其他有效仓库。
- 保留普通仓库、嵌套仓库、Git worktree、路径边界和用户自定义扫描深度行为。

**Non-Goals:**

- 不支持裸仓库、子模块专用界面或任务工作目录外的仓库。
- 不改变提交、发布、同步命令序列和远程选择规则。
- 不让前端传入任意 Git 命令、目录或参数。
- 不并行执行仓库网络查询，也不增加缓存、后台轮询或新的前端状态字段。

## Decisions

### 将后台进程窗口策略移到通用内部组件

把现有平台分发的后台进程配置提取为独立内部组件，由生命周期执行器、任务菜单后台命令和 `internal/repositorygit` 共同调用。Windows 实现继续设置 `HideWindow` 与 `CREATE_NO_WINDOW`，其他平台保持空操作。任务 Git 服务在设置工作目录、环境变量和标准流之后启动进程，窗口属性不得改变输出捕获和错误包装。

不让 `internal/repositorygit` 直接依赖 `internal/lifecycle`。生命周期是业务编排层，仓库服务只需要进程策略；直接依赖会把无关领域耦合在一起，也容易在后续重构中形成导入环。也不在仓库服务中复制 Windows 标志，否则会出现多处平台策略定义。

### 从 `.git` 标记收集候选，再调用 Git 验证

继续使用受深度限制的 `filepath.WalkDir`，但不再对每个目录调用 Git。当遍历遇到名为 `.git` 的非符号链接条目时，将其父目录记录为候选：`.git` 目录对应普通仓库，`.git` 文件对应 Git worktree。`.git` 目录本身不再进入，其他普通目录继续遍历，以保留嵌套仓库发现能力。

遍历结束后仅对去重候选执行 `git rev-parse --show-toplevel`，并继续通过真实路径与相对路径校验确认顶层目录位于任务工作目录内。伪造、损坏或指向工作目录外的 `.git` 候选被跳过。相比对每个目录执行 Git，这种方式将进程数量从“目录数量”收敛到“候选仓库数量”，同时覆盖现有明确要求的普通仓库和 worktree。

不改为只查找 `.git` 目录名称后直接接受父目录，因为 worktree 的 `.git` 是文件，且仅凭文件系统标记不能证明仓库有效或位于安全边界内。

### 默认扫描深度改为 3，并使用一次性设置迁移

将新安装和缺失值的默认 Git 最大扫描深度从 2 调整为 3，使任务目录第 1 层、`workspaces` 第 2 层、项目仓库第 3 层形成一致默认。有效范围仍为 1–10，用户仍可在设置中选择更小或更大的值。

升级时复用现有设置预置迁移版本并增加一个版本步骤：仅当旧版本设置中的扫描深度等于旧默认值 2 时迁移为 3，然后标记迁移完成。旧数据没有记录该值是默认产生还是用户手动选择，因此无法完全区分两者；一次性迁移优先恢复默认功能。迁移完成后用户显式改回 2 时不会再次被覆盖。深度为 1 或 3–10 的旧设置保持不变。

不对扫描器设置隐式最小深度 3，因为这会让用户界面保存的 1 或 2 与实际扫描范围不一致；也不改变默认生命周期的 `workspaces/<项目>` 布局，以免影响现有任务和外部工具约定。

### 区分无效候选与有效仓库状态失败

候选无法通过 Git 顶层目录验证时直接跳过，因为它不是可管理仓库。候选验证成功后，如果读取工作区状态或远程列表失败，服务返回一张 `ActionNone` 的仓库卡片，以相对路径标识仓库并在 `Notice` 中携带可读错误；随后继续处理其他仓库。远程网络查询失败仍沿用现有卡片提示行为。

这样既不会把伪 `.git` 标记展示成仓库，也不会因一个权限异常、锁定或损坏仓库让所有正常仓库消失。现有传输类型与前端卡片已经支持 `notice` 和不可操作状态，因此不增加 Wails 绑定字段。

## Risks / Trade-offs

- [旧版本中手动选择深度 2 的用户会被一次性迁移到 3] → 迁移只执行一次，界面仍可改回 2；这是旧数据缺少“是否默认值”来源信息时保证默认功能可用的取舍。
- [只认 `.git` 标记不会发现裸仓库] → 裸仓库不在既有目标范围内，维持不支持；普通仓库和 worktree 均有对应标记。
- [损坏仓库仍会产生少量 Git 进程] → 只对候选执行验证，进程数与候选数相关，不再与普通目录数相关。
- [状态失败卡片不可操作] → 保留路径和错误可见性，用户修复仓库后可点击现有刷新按钮重新读取。
- [通用进程组件移动影响多个调用方] → 保持函数签名和平台实现不变，并分别运行 Windows 交叉编译、平台属性测试和现有生命周期/任务菜单测试。

## Migration Plan

1. 引入通用后台进程配置组件并迁移现有调用方，先验证现有 Windows 行为不变。
2. 调整仓库候选发现、状态失败隔离和默认深度，增加对应测试。
3. 增加设置迁移版本；加载旧数据时将旧默认深度 2 一次性更新为 3并持久化。
4. 通过 Windows 构建测试确认任务 Git 进程包含无窗口属性，再用 `wails dev` 在 Windows 上验证 Git 标签没有黑框且能发现 `workspaces/<项目>`。

回滚代码时，已迁移为 3 的扫描深度仍是旧版本允许的合法值，无需反向数据迁移；用户也可在设置中手动改为 2。
