## Context

`TaskTree` 已为每个任务行计算已保存的任务颜色，并将其用于 4px 左边框、选中行的内描边以及开始任务时的短暂反馈。普通、未选中的任务行背景目前为透明，任务颜色无法延伸到内容区域。后端将任务颜色规范化为六位十六进制值，前端现有开始反馈也通过在该值后附加 alpha 字节产生同色背景。

本变更只调整任务树行的常态视觉层级。任务的颜色数据、主题色、选中语义、指针拖拽和生命周期反馈均须保持原有行为。

## Goals / Non-Goals

**Goals:**

- 让每个未选中的任务行以自身左侧色条的约 4% 透明度显示极浅背景。
- 维持亮色和暗色模式下的文本、图标和任务色可辨性。
- 保留选中、悬停、拖拽和任务开始反馈各自已有的优先级。

**Non-Goals:**

- 不改变任务颜色调色板、默认颜色、持久化格式或后端颜色校验。
- 不为终端子项、搁置任务分组、拖拽预览或详情区引入任务色铺底。
- 不改变任务树布局、操作、无障碍标签或动画时序。

## Decisions

### 1. 只为未选中的顶层任务行添加同色常态背景

在任务行已有的 `sx` 样式中，以 `taskColor` 派生常态背景；任务色左边框继续直接使用同一个值。已选中行继续使用 `action.selected`，由现有同色内描边保持与任务色的关联；悬停、拖拽和开始反馈则继续使用各自已有规则。

这样任务色既能把色条和内容归为一体，又不与表示“当前选择”的主题背景竞争。将同色背景应用到所有行状态的备选方案会弱化选择态，并可能覆盖开始反馈，因此不采用。

### 2. 使用 `#RRGGBB0A` 表示约 4% 的不透明度

任务颜色由后端规范化为六位十六进制值，前端现有开始反馈已经追加 alpha 字节。常态背景采用同一形式，并追加 `0A`，即约 4% alpha；这是低于反馈首帧 `14`（约 8%）的固定、可复核基线。

使用 `color-mix()` 的备选方案能表达相同结果，但会新增 CSS 变量或解析分支，而当前输入契约已经确保值可安全派生八位十六进制颜色，因此不采用。

### 3. 以组件渲染测试锁定颜色关联和状态边界

扩展 `TaskTree` 的现有任务颜色标记测试，断言普通任务行同时具有给定任务色的左边框和极浅同色背景。再覆盖选中或开始反馈分支，确保常态底色不会替换其已有的语义背景或动画样式。

视觉上在亮色和暗色主题下进行人工走查；此改动不引入可访问名称或交互逻辑变化，因此无需新增接口或端到端流程。

## Risks / Trade-offs

- [浅色任务颜色在亮色模式下几乎不可见] → alpha 限制为约 4%，将其定位为辅助关联而非状态标识，左侧 4px 色条仍是主要标记。
- [常态背景覆盖选中或反馈状态] → 仅在未选中行设置底色，保留现有选中、悬停、拖拽与反馈规则的优先级。
- [未来允许非六位十六进制任务色] → 在扩展颜色格式时一并替换 alpha 派生方式；当前后端校验保证该假设成立。

## Migration Plan

无需数据迁移或发布顺序调整。上线后，所有已有任务会立即使用已保存颜色渲染极浅背景；回退时移除该常态样式即可，不影响任务记录。
