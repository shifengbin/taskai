## Context

任务模板定义与当前模板选择保存在同一个 `Settings` 对象中，并通过普通 `SaveSettings` 绑定持久化。该绑定支持未携带模板字段的旧客户端与非模板设置调用；前端类型也将两个模板字段声明为可选。

当前应用层会先调用完整设置归一化。归一化将缺失的 `TaskTemplates` 切片变成非 `nil` 的空切片，导致仓储层无法再区分“模板字段未提交”和“用户明确提交空模板集合”。它随即保存空集合和空当前模板选择。加载只读取已持久化状态，不能安全地从任务值重建用户定义，因此设置弹窗会持续显示空模板。

## Goals / Non-Goals

**Goals:**

- 保留模板快照缺失与显式删除之间的语义差异。
- 让普通设置保存、重新打开设置和重启应用都保留未提交的模板定义及当前选择。
- 保持显式编辑模板、切换当前模板和删除全部模板的既有能力与校验。
- 在应用绑定、仓储和前端设置交互层建立回归覆盖。

**Non-Goals:**

- 不从已经丢失的数据中推断或恢复自定义模板定义。
- 不修改任务模板、任务记录或 Wails 公开数据格式。
- 不引入跨进程设置版本控制或解决所有并发设置冲突。

## Decisions

### 1. 在应用层校验前合并缺失模板快照

`App.SaveSettings` MUST 在调用完整设置校验前读取当前持久化设置。若传入的 `TaskTemplates` 为 `nil`，它将把当前模板集合和当前模板标识复制到待校验设置；若传入非 `nil` 集合，则保留请求中的集合和标识，并执行模板更新校验。

这保留了字段存在性信息，并保证状态 HTTP 配置比较和后续仓储保存看到的是完整、可校验的设置。仓储层保留自身的缺失快照保护，以支持直接调用仓储的现有契约，但不再是唯一的保护点。

备选方案是在 `Settings` 中改用指针或引入专用请求 DTO 记录 JSON 字段存在性。这能把语义表达得更显式，但会扩大 Wails 生成模型和所有调用方的改动；在当前绑定边界由 `nil` 切片表达缺失已足够。

### 2. 将模板集合与当前模板选择作为一个提交单元

前端只有在拥有 `taskTemplates` 快照时才向普通设置保存请求写入 `taskTemplates` 和 `activeTaskTemplateId`。仅存在空的当前模板标识不能生成空模板集合；这种不完整请求应交给后端按“未提交模板”处理。

设置草稿从已加载设置初始化或补全时，模板集合与当前选择一起复制，避免由局部设置编辑意外构造没有模板字段的草稿。用户在任务模板标签页编辑后的空数组仍会随请求发送，代表有意删除最后一个模板。

备选方案是让每个普通设置请求始终发送完整模板快照。它可以减少缺失字段，但旧客户端、错误恢复路径和未来调用方仍可能发送不完整请求，因此不作为服务器端保护的替代。

### 3. 通过持久化边界验证行为

测试从含有模板和当前选择的已保存设置开始，提交只修改工作区、Shell、面板宽度或状态的设置请求，然后重新加载设置并重新打开模板设置界面。测试断言模板定义和当前选择保持不变。

另外覆盖显式空模板集合，以确认保护机制不阻止合法删除；覆盖 API 包装的字段裁剪，以确认 `activeTaskTemplateId` 单独存在时不伪造空模板集合。

## Risks / Trade-offs

- [旧调用方依赖缺失模板字段清空模板] → 缺失字段从未是明确删除操作；调用方必须发送空集合与空当前选择来删除，符合现有设置界面的语义。
- [已丢失自定义模板无法自动恢复] → 不尝试从任务字段猜测名称、显示文本或类型；向用户说明需从备份恢复或重新创建。
- [前后端同时修改模板] → 当前改动只保护字段缺失，不提供完整乐观并发控制；显式提交仍遵循现有最后写入和活动任务引用校验。

## Migration Plan

1. 先添加覆盖缺失模板快照与显式删除的失败回归测试。
2. 在应用绑定和前端请求构造处保留字段存在性，并确保草稿补全模板对。
3. 运行 Go、前端测试与生产构建；无需迁移数据文件。
4. 回滚时仅还原代码。已经被旧版本持久化为空的自定义模板不能自动恢复，应从备份恢复或重新创建。
