## 上下文

本机 HTTP 服务可由两种独立条件启动：状态管理方式选择 HTTP，或在标题变化状态管理下显式启用独立服务。应用层已经以这两个条件决定 HTTP 服务器的生命周期，且 `statusHTTP.APIURL()` 仅在服务器实际监听时返回状态 API 基址。

普通终端、显示终端的自定义任务命令和菜单中的显示终端命令均复用 `terminalStatusEnvironmentBuilder`。目前该构造器仅在状态管理方式为 HTTP 时追加 `TASKAI_STATUS_API`，因此独立服务已监听时会遗漏该变量。进程环境在终端创建时固定，既有终端不能被设置变更追溯更新。

## 目标 / 非目标

**目标：**

- 本机 HTTP 服务实际监听时，所有之后新建的终端获得 `TASKAI_STATUS_API=<当前 API 基址>`。
- 保持普通终端、显示终端命令和菜单显示终端命令的一致注入行为。
- 在服务未监听或监听配置失败时不注入空值或过期地址。
- 使任务详情、HTTP 帮助和 README 的变量范围与运行时行为一致。

**非目标：**

- 不新增或重命名 `baseURL`、`BASE_URL`、`TASKAI_BASE_URL` 等环境变量。
- 不向无终端菜单命令、前置/后置脚本或生命周期自定义 Shell 命令注入 `TASKAI_STATUS_API`。
- 不改变生命周期首条自定义命令从标准输入接收 `baseURL` 的协议，也不改变已有终端的环境。
- 不变更 HTTP 路由、端口配置、状态汇总或持久化数据格式。

## 决策

### 1. 以实际 API 地址决定注入

终端环境构造在保留任务和终端 ID 后直接读取 `statusHTTP.APIURL()`：返回非空地址时追加 `TASKAI_STATUS_API`，为空时保持现有基础环境。状态管理方式和独立服务开关继续只负责服务生命周期，不再作为环境变量的二次条件。

相比依据 `HTTPServiceEnabled || StatusManagementMode == http` 重新推导，该方式直接反映监听是否成功、端口是否仍可用和服务是否已关闭，且与生命周期首段输入追加 `baseURL` 的可用性语义一致。

### 2. 复用现有变量与终端构造边界

继续使用 `TASKAI_STATUS_API`，值保持 `/api/v1` 基址。所有终端创建入口已经统一经过 `terminalStatusEnvironmentBuilder`，因此只调整该构造器即可覆盖普通终端、显示终端的自定义命令和任务菜单中的显示终端命令。

新增 `TASKAI_BASE_URL` 会让同一地址出现两个权威变量，并要求使用方选择；向生命周期或无终端路径扩展则会改变已经记录的环境变量边界，均不在本次最小修复范围内。

### 3. 明确进程创建时的快照语义

帮助与任务详情将说明：变量注入依赖本机 HTTP 服务监听，且只作用于之后新建的终端。切换端口、服务开关或状态管理方式不会修改已运行 shell 的进程环境。

## 风险 / 权衡

- [用户在已有终端中仍找不到变量] → 文档明确环境只在创建进程时注入，并保留“新建终端后再使用新配置”的提示。
- [HTTP 服务启动失败但设置值显示为启用] → 仅当 `APIURL()` 非空才注入，不暴露不可访问的地址。
- [变量名带有“STATUS”但接口也提供任务查询] → 保持现有公开变量以避免兼容性和文档分叉；通用 API 环境变量留待独立需求讨论。

## 迁移计划

1. 更新终端环境构造和后端测试，覆盖独立服务、HTTP 状态管理、服务关闭及已有终端不回写的边界。
2. 同步任务详情、HTTP 帮助和 README 的变量说明，并运行前后端相关测试。
3. 发布后用户只需新建终端即可获得变量；无需迁移设置或任务数据。
4. 若需回滚，恢复原有状态管理方式判断即可，已有环境变量和持久化数据不受影响。

## 未决问题

无。本变更只统一终端与已监听本机 HTTP 服务之间的现有变量契约。
