## Context

生命周期命令链已经具备命令冻结、逐条执行、持久化执行记录和 Wails 事件的基础能力，但 `StartTask`、`FinishTask`、`UpdateTask` 与重试绑定都会在同一调用内等待完整链结束。编辑表单只能在绑定返回后关闭；进度事件与最终返回值的相对到达顺序也没有可依赖的前端约束。

现有执行记录包含钩子、链、命令 ID、名称、序号、状态和错误，但失败记录构造时没有复制命令名称。任务记录存在执行记录时已能锁定任务操作，任务树也已按 `running` 与 `failed` 区分状态并只在失败时提供重试。此次变更要保留命令链的串行语义、钩子时序、失败不回滚规则与从链首重试规则，同时让运行状态成为绑定返回后的稳定事实。

## Goals / Non-Goals

**Goals:**

- 每个生命周期链在命令真正执行前持久化可展示、可锁定的运行记录，并让绑定立即返回该任务快照。
- 对运行、每一步进度、成功清理与失败记录发布有序任务事件；失败记录精确指向失败命令。
- 保持五个钩子的既有业务时序：前置链成功后才改变任务状态，后置和更新链失败不回滚已保存业务数据。
- 让执行中任务更新在业务数据保存后立即关闭编辑弹窗，同时保持任务菜单禁用到链成功或失败。
- 在接口返回与后台事件交错时避免前端显示回退到较旧进度。

**Non-Goals:**

- 不增加取消、暂停、并行、条件分支、命令输出日志或跨重启恢复外部进程。
- 不改变命令的标准输入输出传递、工作目录、安全校验、链适用范围或重试从首条命令开始的行为。
- 不在任务树展开整条命令链；界面只显示当前钩子、当前命令和 `序号/总数`。

## Decisions

### 1. 以“调度”和“执行”两阶段取代同步 `runLifecycleHook`

应用层新增统一的调度入口：它在任务锁定检查后读取当前链定义、冻结该轮命令和输入上下文、创建运行记录并写入持久化存储。调度成功立即返回带运行记录的任务快照，随后由单独的后台工作器执行已冻结的命令。

不直接把当前 `runLifecycleHook` 放入 goroutine。那会让运行记录、命令快照和后续状态转换与调用返回之间产生竞态。两阶段入口必须先完成运行记录持久化，才能启动工作器；这样前端收到成功响应时已能确定地禁用操作并显示第 `1/N` 步。

链不存在、无法构造输入等调度前错误仍在调用内写入失败记录并返回；已经开始的外部命令错误则由工作器写入失败记录。无链选择时保持原有的同步空操作返回。

### 2. 为每次执行添加运行标识和单调进度版本

`LifecycleExecution` 新增一次性运行标识与从 1 开始递增的进度版本。调度创建新标识和版本 1；每次进入命令、成功清理或失败写入均推进版本。存储更新必须仅接受当前运行标识，防止旧工作器覆盖已经重试的新一轮记录。

Wails 生命周期事件和绑定返回均携带完整任务快照。前端按任务 ID、运行标识和版本合并：同一运行标识中较低版本不能覆盖较高版本；新运行标识始终代表一次新的重试。这样即使后台快速推进到第 2 步后接口第 1 步的返回才抵达，也不会令显示回退。

旧快照缺少这两个字段时保持可读；它们只用于新的运行和事件合并，不影响旧失败记录的重试资格。

### 3. 用后台续接器保持五种钩子的状态机

工作器成功后由钩子续接器处理后续业务步骤：

- `beforeStart` 成功后提交任务为执行中、注册实时状态，再调度 `postStart`。
- `postStart` 成功后清除执行记录。
- `beforeEnd` 成功后关闭终端并提交任务为已完成，再调度 `postEnd`。
- `postEnd` 成功后清除执行记录。
- `updateTask` 在编辑数据已保存后调度；成功后清除执行记录，失败不回滚编辑数据。

重试根据失败钩子重新读取任务和最新链定义，创建新的运行标识，并进入相同的续接器。`beforeStart` 和 `beforeEnd` 重试继续分别使用准备开始与完成任务的路径；其他钩子直接重调度。每个任务的调度与续接由任务级互斥保护，避免同时触发两个生命周期链。

选择后台续接器而不是在前端串联多个绑定调用，能让状态机、持久化锁和进程重启恢复规则仍由后端统一掌控。

### 4. 失败记录必须保留当前命令的可显示身份

运行器每次调用进度回调时写入命令 ID、命令名称、序号和总数。发生执行错误时，失败记录从当前运行记录复制这四项及运行标识、版本和错误文本；链解析错误没有命令名称时才允许界面使用通用“命令”后备名称。

这样任务树和详情可在失败时以红色标记实际失败命令，并将错误消息放在提示或详情面板内。重试按钮仅在状态为 `failed` 时显示；运行状态使用非错误颜色且不显示重试。

### 5. 前端以持久化运行状态驱动弹窗和任务列表

编辑执行中任务时，保存响应代表业务数据和运行记录都已持久化，前端立刻更新任务、清空草稿并关闭弹窗，不等待命令链。生命周期事件负责随后步骤、成功和失败的刷新。

开始任务的 `beforeStart` 运行时任务仍处于未执行标签，结束任务的 `postEnd` 运行时任务已处于已完成标签。事件处理器在选中任务发生这两种状态迁移时同步当前标签，确保进度在对应任务列表中持续可见。运行或失败记录存在时，任务树的拖放、右键菜单、任务操作、编辑以及开始/结束按钮均保持禁用；失败时仅额外显示重试。

## Risks / Trade-offs

- [应用退出会中断后台工作器] → 保留运行记录；下次启动时沿用现有迁移策略将其标为失败，并保留命令身份和“应用重启中断命令链”错误以供从首条重试。
- [后台事件与绑定返回乱序] → 通过运行标识和单调进度版本在服务端条件写入、前端合并两侧阻止回退。
- [异步状态机引入并发入口] → 使用任务级调度互斥和基于运行标识的条件更新，所有状态转换仍经过应用层续接器。
- [重试重复执行外部副作用] → 延续原有从首条命令重试语义；系统目录命令保持幂等，自定义命令仍由配置者设计幂等性。
- [详情接口增加内部版本字段] → 字段为向后兼容的附加信息，现有客户端可忽略；类型和自动绑定同步更新。

## Migration Plan

1. 扩展任务执行记录的 JSON 模型与规范化逻辑，使缺失运行标识和版本的旧快照可正常读取。
2. 先实现调度、工作器、续接器和重启中断记录，再让全部绑定调用改用统一入口。
3. 更新 Wails 前端类型、事件合并与任务树状态，确保保存响应和事件乱序不回退。
4. 运行 Go、前端测试及项目构建脚本；若发布后需要回滚，旧二进制会忽略新增 JSON 字段，正在执行的后台进程随应用退出并在新版本启动后按失败记录处理。

## Open Questions

无。任务树采用当前步骤加 `序号/总数` 展示，不新增完整步骤列表。
