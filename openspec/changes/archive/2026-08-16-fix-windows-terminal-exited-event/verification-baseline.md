# 验证基线：exited 事件不到达（Windows 10.0.26200.9168）

## 现象

- 嵌入终端里 cmd 自然退出（输入 `exit`）后，前端长时间收不到 `exited` 事件；Go 侧集成测试等待 10 秒超时。
- 同机此前版本行为正常；CI（windows-latest 稳定构建）从未运行过 `go test`，无护栏。

## 分层证据（独立探针程序，.probe，已随修复删除）

1. **进程等待层正常**：`process.Wait()` 在写入 `exit` 后约 9ms 返回，退出码 0。进程退出本身没有问题。
2. **读循环被卡住**：ConPTY 输出管道上的阻塞 `ReadFile` 在进程退出 5-8 秒后仍不返回（多数情况下永不返回）。该构建的 conhost 不因客户端退出而关闭输出管道。
3. **仅关伪控制台即可解除阻塞且不丢数据**：在进程退出后只调用 `ClosePseudoConsole`（不动管道句柄），读循环立即排空全部剩余输出（含 `FINALMARKER` 探针标记），随后收到错误 109（"The pipe has been ended"）。这证明 conhost 在伪控制台关闭时会冲刷最终输出并结束管道。
4. **捆绑关闭会丢数据**：进程退出后立即调用库的 `Close()`（关伪控制台 + 关两端管道 + 删属性表一次完成），20 次循环全部丢失 banner 之后的输出——conhost 以约 18ms 的节奏分批冲刷，读端管道先被关掉，最终输出就没了。

## 结论与修复形态

- 根因：conhost（26200 构建）不主动结束 ConPTY 输出管道 → 读循环不退出 → 管理层在读循环之后的 `exited` 发布被卡住。
- 修复：由后端自己管理两阶段拆卸——进程退出后先只关伪控制台（触发冲刷+管道结束），读循环排空并退出后再释放属性表与全部句柄。
- 库（charmbracelet/x/conpty v0.1.0/v0.2.0）的 `Close()` 是一次性的捆绑关闭，结构上表达不出两阶段，因此移除依赖、直接使用 golang.org/x/sys/windows 管理。

## CreateProcess 排错记录（实现期）

- 环境块不能经 `UTF16PtrFromString` 构造（内嵌 NUL 返回 EINVAL，表面现象是"invalid argument"），必须手工拼接 `[]uint16`。
- 伪控制台属性的值必须把**句柄值本身**作为指针传入（与 Win32 示例、与库一致）；传句柄变量的地址会让内核拿到假的控制台，子进程控制台子系统初始化失败（`0xC0000142` STATUS_DLL_INIT_FAILED）、无任何输出即退出。为通过 `go vet`，用存储重解释（`*(*unsafe.Pointer)(unsafe.Pointer(&h))`）完成句柄值到指针的转换。
