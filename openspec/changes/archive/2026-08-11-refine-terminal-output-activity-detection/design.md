## Context

当前后端在收到任意非空 PTY 输出时立即调用实时状态服务。该做法无法区分实际画面变化与光标移动、标题设置或仅改变后续输出属性的控制序列。前端已为每个收到输出的终端维护 xterm 会话；xterm 会在解析输出后提供其活动缓冲区，能够作为用户可见终端画面的事实来源。

## Goals / Non-Goals

**Goals:**

- 在 `output-change` 方式下，只有解析后终端画面的内容或内容颜色、样式实际变化才触发活动。
- 将空格等空白单元格作为画面内容的一部分；空白覆盖文字、空白背景颜色变化和滚动都能触发活动。
- 忽略光标位置、光标形态、闪烁、标题、响铃和未作用到画面的样式设置。
- 保留实时状态服务现有的模式校验、1.5 秒静默与任务聚合规则。

**Non-Goals:**

- 不改变终端输出保留、PTY 协议、终端主题配置或状态持续时间。
- 不将光标的任何变化视为活动。
- 不改变 `title-change` 或 HTTP 状态管理方式的活动来源。

## Decisions

### 在前端 xterm 解析后检测画面变化

`TerminalSessionRegistry` 在创建会话时建立初始画面快照，并在 xterm `onWriteParsed` 回调中比较更新后的活动缓冲区。快照覆盖当前可见行、活动缓冲区类型、视口位置和每个单元格的字符、宽度、前景色、背景色及可见文本样式；空白单元格也保留在快照中。光标坐标和光标选项不在快照内。

选择该方案是因为 xterm 已完整处理跨片段 ANSI 序列、宽字符、Tab、擦除、滚动和颜色属性，比较结果与实际终端画面一致。仅在 Go 端解析原始 PTY 数据无法可靠重现这些状态，且会把不改变画面的控制序列误认为活动。

### 以解析批次而非原始数据块上报活动

`onWriteParsed` 最多每帧通知一次。每次回调仅在画面快照发生差异时调用新的 Wails 绑定，由 `App` 转交给现有 `ReportOutputActivity`。后端继续以 `ModeOutputChange` 拒绝其他方式的调用，并管理计时器。

这会合并高频输出，避免为同一帧内的多个 PTY 块重复比较和跨进程调用。若同一解析批次内的临时画面变化最终恢复原状，则不触发活动，因为用户不会看到最终画面差异。

### 移除原始输出的后端活动上报

`App.publishTerminalEvent` 保留向前端转发原始终端事件的职责，但不再因 `event.Data` 非空而直接上报活动。前端保存的状态管理方式为非 `output-change` 时不发起画面活动调用；后端模式检查仍是防止设置切换竞态的最终边界。

### 控制比较成本并维护基线

比较范围限制在当前可见网格，不扫描滚屏历史。会话初始化、终端尺寸变化、会话销毁和仅由界面引起的重新适配会重建快照基线，不产生活动。现有注册表会在输出到达时创建后台会话，因此未选中的终端也能使用相同的解析和判定路径。

## Risks / Trade-offs

- [可见网格尺寸较大且多终端同时输出] → `onWriteParsed` 将每个终端的比较限制为最多每帧一次，且只扫描 `行 × 列` 个单元格，不随滚屏历史增长。
- [xterm 异步解析使输出与退出事件紧邻] → 会话销毁时取消监听并清理快照；退出状态仍由既有后端事件处理，不依赖画面活动。
- [终端尺寸或主题变化造成重新渲染] → 主动重置基线，避免把用户界面操作当作 PTY 活动。
- [动态调色板控制可能影响既有字符的实际颜色] → 测试覆盖项目支持的 ANSI 单元格颜色重写；若 xterm 对动态调色板的公开状态不足以比较，则将其作为后续独立变更处理，避免依赖私有 API。
