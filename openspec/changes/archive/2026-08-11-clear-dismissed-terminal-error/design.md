## Context

终端实时状态由 `internal/realtime.Service` 在内存中维护，并按终端状态聚合为任务状态。终端自然退出时，应用层将该终端标记为 `error` 并保留实时状态记录，任务树收起后显示任务级异常点；用户在任务树中明确关闭异常终端时，前端会删除终端条目，但当前应用层的 `CloseTerminal` 只调用终端管理器。

终端管理器对已退出会话的关闭调用是幂等成功返回，不会重新发布退出事件。因此，异常终端的实时状态不会自动进入 `RemoveTerminal` 路径，任务级异常状态会残留在当前应用会话中。任务状态和终端实时状态均不应写入持久化任务数据。

## Goals / Non-Goals

**Goals:**

- 用户成功关闭异常退出终端后，将该终端从实时状态服务移除。
- 通过现有版本化实时状态事件把移除后的任务聚合状态投影到前端。
- 保持关闭操作幂等、终端原始退出原因准确，以及现有前端终端条目清理行为。
- 用测试覆盖异常退出后关闭、活动终端关闭和任务状态恢复。

**Non-Goals:**

- 不改变异常退出首次发生时的红色异常提示。
- 不把实时状态、终端历史或“已关闭”标记持久化到任务数据。
- 不新增用户可见的状态重置按钮或新的 Wails API。
- 不改变任务生命周期状态、终端输出、右侧终端视图或关闭失败时的错误处理。

## Decisions

### 在应用层处理用户关闭后的状态清理

`App.CloseTerminal` 在终端管理器成功返回后调用 `app.realtime.RemoveTerminal(taskID, terminalID)`。应用层最清楚这是用户主动关闭动作；实时服务已有移除逻辑，会停止计时器、删除终端并发布新的任务聚合状态。移除返回值不作为错误处理条件，因为活动终端的退出事件可能已经先完成移除，重复调用应保持幂等。

备选方案是让 `terminal.Manager.Close` 对已退出会话重新发布 `ExitReasonClosed` 事件，但这会把真实的自然退出原因改写成手动关闭，且把 UI 的状态确认职责下沉到通用 PTY 管理器，因此不采用。

### 保持现有实时事件作为前端事实来源

前端继续在关闭调用成功后立即移除本地终端条目，并通过现有 `task-realtime-status:event` 处理任务状态更新。后端 `RemoveTerminal` 产生的版本号高于此前的异常事件；前端已有版本过滤逻辑，因此旧的异常事件不能覆盖新的清理结果。

备选方案是前端在 `closeTerminal` 中直接把任务的 `realtimeStatus` 改为 `idle`，但这会绕过后端聚合规则，在任务仍有其他工作中、未读或异常终端时产生错误结果，因此不采用。

### 测试用户确认和聚合优先级

测试应区分两种时序：异常事件已经发布后再关闭已退出会话，以及活动会话直接关闭。前者必须验证任务状态从 `error` 恢复为 `idle`；后者必须验证现有退出事件与额外清理调用不会破坏正常行为。若任务仍有其他终端，清理一个异常终端后应保留其余终端的最高优先级状态。

## Risks / Trade-offs

- [实时事件到达顺序] 前端可能先收到异常事件再收到移除事件，短暂显示红点是允许的；版本号保证最终状态收敛到移除后的聚合结果。
- [重复移除] 活动终端关闭可能由终端退出事件先移除，随后应用层再次调用移除；忽略 `false` 返回值可保持幂等，但测试必须覆盖该时序。
- [错误恢复范围] 只有用户明确关闭终端才会清除异常；终端异常退出但未关闭时继续显示红点，保留问题提醒语义。

## Migration Plan

无需数据迁移。发布新版本后，实时状态服务按新逻辑处理后续关闭动作；已存在的残留状态在应用重启时自然清空，或由用户再次关闭对应异常终端时清理。回滚仅需恢复应用层关闭逻辑，不影响持久化任务数据。

## Open Questions

无。现有实时状态服务的移除事件和前端版本过滤已经满足所需投影能力。
