## Context

任务菜单配置当前包含“编辑任务”“新增终端”和“打开任务文件夹”三个系统项。设置规范化会重建这些系统项，因此用户保存的名称不会保留。搁置切换不属于配置列表，而是在任务树菜单的末尾单独渲染；它会随任务状态在“搁置任务”和“取消搁置”之间切换。

本变更需要让四个系统操作都能改名，并让搁置切换与其他系统项使用同一排序。任务菜单仍会同时用于右键菜单和“任务操作”下拉菜单；执行状态、生命周期锁定和已有图标规则不能改变。

## Goals / Non-Goals

**Goals:**

- 保存并显示所有系统任务菜单项的自定义名称。
- 为搁置切换保存未搁置与已搁置两套名称，并允许它参与菜单排序。
- 通过设置规范化补齐旧配置，且只允许名称字段影响系统项。
- 在两种菜单入口中一致地显示名称、排序、图标和可用性。

**Non-Goals:**

- 不允许修改、删除或新增系统操作的行为。
- 不改变搁置状态持久化、任务排序、终端创建、打开目录或生命周期锁定规则。
- 不为自定义命令增加新的配置字段，也不改变其编辑器。

## Decisions

### 将搁置切换建模为系统菜单项

新增 `toggle-shelved` 系统类型及稳定 ID `system.toggle-shelved`，默认排在现有三个系统项之后。它只在未锁定的执行中任务菜单中渲染；未搁置任务触发搁置，已搁置任务触发取消搁置。

选择该方案而非在设置中维护独立标签映射或继续保留菜单末尾的特殊 JSX，因为它使排序、默认补齐和两个菜单入口都复用同一菜单列表。独立映射会分裂菜单的顺序和名称来源；特殊 JSX 则不能满足搁置项可排序的需求。

### 保留系统项行为，只持久化允许编辑的文本

`TaskMenuItem` 对所有系统项继续保存 `Name`。搁置切换额外保存 `UnshelveName`，分别表示未搁置任务和已搁置任务看到的名称；默认值为“搁置任务”和“取消搁置”。

后端根据 ID 重新确定每个系统项的类型及不可变字段，仅从用户配置接收修剪后的名称。所有名称必须非空；搁置项的两个名称都必须非空。自定义命令沿用既有校验逻辑。这样名称可自定义，但系统项不可能被伪装成命令、携带脚本或开启终端。

选择 `UnshelveName` 而非只保存一个通用名称，因为两种状态代表相反的动作。让它们独立命名既满足可理解性，也符合已确认的交互需求。

### 在同一个设置编辑器中按类型收敛字段

菜单管理列表中，系统项和自定义项都提供“编辑”入口。编辑普通系统项时只显示一个“菜单名称”字段；编辑搁置项时显示“搁置任务名称”和“取消搁置名称”两个字段。系统项不显示命令、参数、终端、脚本和删除控件，自定义命令继续使用已有表单。

前端将设置保存后返回的规范化配置作为新的状态来源。任务树按保存的顺序遍历菜单项，并在搁置项渲染时依据 `task.shelved` 选择相应名称与现有收纳或恢复图标。

### 兼容现有设置

空的菜单配置仍返回完整默认列表。仅含原三个系统项的旧配置会保留其顺序和名称，并在末尾补上默认搁置项。新字段缺失时使用默认值；用户提交的空白名称则被拒绝，不保存部分设置。

## Risks / Trade-offs

- [旧设置中的系统项名称可能为空] → 仅对缺失的搁置项补默认；用户明确提交的空白系统名称返回校验错误，避免悄然产生无名称菜单项。
- [菜单项增多可能影响小视口] → 复用现有菜单高度限制和内部滚动，不改变定位计算。
- [系统项编辑器与自定义命令编辑器混淆] → 按项类型隐藏不可用字段，并用“系统固定操作”说明操作不可改变。
- [前端名称与后端规范化不一致] → 保存后始终使用后端返回的完整设置刷新草稿和运行时菜单。

## Migration Plan

1. 扩展设置模型、默认菜单列表和规范化逻辑，令旧的三项配置自动补齐搁置项。
2. 更新生成的 Wails 类型和前端默认值，使新旧设置都能安全读取。
3. 发布时由现有设置读取与保存流程完成迁移；不需要单独的数据迁移命令。
4. 如需回退代码，设置文件中多出的搁置项和 `unshelveName` 会作为 JSON 未知字段被旧版本忽略，旧版本继续使用自己的默认菜单行为。

## Open Questions

无。搁置和取消搁置名称分别配置、搁置项可排序以及验收范围均已确认。
