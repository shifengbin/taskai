## 背景

任务树按 `pending`、`running` 和 `completed` 三种生命周期状态筛选任务；执行中任务当前直接按持久化数组顺序展示，并允许在同一状态内拖动排序。任务数据保存在本地 JSON 文件中，而设置数据只存放全局偏好。终端、实时状态和任务生命周期均以任务的 `running` 状态为准。

本变更需要提供一种可重启后保留的展示分组，但不得改变任务生命周期、终端活动或实时状态处理。同时，取消搁置后必须稳定地追加到正常执行中列表末尾。

## 目标与非目标

**目标：**

- 持久化执行中任务的搁置标记，并保持旧数据兼容。
- 在执行中标签的末尾以同级折叠区展示搁置任务。
- 通过单次原子写入同时完成搁置标记和执行中任务顺序调整。
- 保持现有正常执行中任务的拖动排序、终端操作与生命周期行为。

**非目标：**

- 不增加“已搁置”任务状态，不暂停、关闭或隐藏任务终端。
- 不提供搁置任务之间的拖动排序或跨状态拖动。
- 不持久化折叠区的展开状态，也不新增 HTTP API。

## 决策

### 将搁置状态归属到任务

在任务模型中增加布尔型 `shelved` 字段，缺失字段按 `false` 处理。任务是搁置选择的唯一所有者，随任务 JSON 一同持久化；相比在全局设置中保存任务 ID，此方式不会遗留已结束或删除任务的引用，也无需跨配置清理。

该字段只允许在任务处于 `running` 且未被生命周期命令链锁定时修改。开始和结束任务会清除该字段，保证未执行和已完成任务不会带有无意义的搁置标记。

### 使用原子服务操作维护标记和顺序

新增设置任务搁置状态的应用绑定，由生命周期服务在一次加载、校验和保存中完成。操作会从当前执行中任务的持久化顺序中拆分出正常任务与搁置任务，移除目标任务后按新状态追加到相应分组末尾，再将组合后的顺序回写到原有执行中任务的位置。

操作返回完整任务列表，而非只返回目标任务。前端据此整体替换任务状态，确保界面中的正常任务和搁置任务顺序与已持久化数据一致。单独更新标记再由前端排序会产生两次写入，且在失败或进程中断时可能使恢复位置不正确，因此不采用。

### 在任务树中渲染同级折叠区

任务树仅在 `running` 标签下将可见任务拆分为正常任务与搁置任务。正常任务沿用现有的顶层任务条目；若存在搁置任务，则在其后追加一条同级的“已搁置（n）”折叠区。折叠区初始为收起状态，仅保存在当前前端会话内；展开后显示完整的原有任务条目和终端子节点。

搁置区不参与正常任务的拖动目标计算，也不提供拖动排序。正常任务的重排请求仍需包含同一状态的完整顺序，前端会保留搁置分组的现有顺序以满足现有后端校验。

### 通过现有任务操作菜单切换

执行中且未锁定的任务操作菜单根据 `shelved` 显示“搁置任务”或“取消搁置”。复用现有菜单避免在每个任务行新增常驻按钮。生命周期命令链执行或失败锁定期间，菜单与服务端校验均拒绝切换；前端在调用失败后保持原列表并显示已有的错误提示。

## 风险与取舍

- [旧状态文件缺失字段] → Go 布尔值零值为 `false`，加载旧数据自动视为未搁置。
- [标记与排序写入分离] → 服务端只提供原子操作并返回完整列表，避免顺序与展示不一致。
- [异步调用期间生命周期状态变化] → 应用层禁用锁定任务的操作，服务层再次校验状态和锁定条件后才写入。
- [折叠区增加任务树复杂度] → 复用既有任务条目渲染与终端子树，仅在外层组织两个列表。

## 迁移计划

部署后，已有任务无需迁移；缺失的 `shelved` 字段按未搁置处理。若需回退到旧版本，旧版本会忽略该 JSON 字段，任务状态和终端数据保持可读。
