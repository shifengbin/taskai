## Context

TaskAI 已将任务右键菜单与“任务操作”下拉菜单统一建模为持久化的 `TaskMenuItems`。自定义命令项已经支持名称、命令、逐项参数、显示终端和任务操作目录，因此新增代理入口不需要新的前端类型或 Wails 方法；缺失的是应用启动后的命令检测和设置合并。

检测必须在 Linux、macOS 与 Windows 上保持一致。Windows 的 npm 或其他安装方式可能把命令暴露为 `.cmd` 包装文件，而现有 Windows ConPTY 后端对带 `Command` 的请求直接调用解析结果，没有使用请求中的配置 Shell；实现时必须确保“检测成功”与“菜单可以启动”一致。

## Goals / Non-Goals

**Goals:**

- 每次启动独立检测 `codex` 与 `claude`，并幂等补充准确的显示终端菜单项。
- 只追加缺失的自动项，保留全部已有设置、用户修改和菜单顺序。
- 让同一设置及执行路径在 Linux、macOS 和 Windows 上生效，包括 Windows 命令包装文件。
- 将检测、合并和平台命令启动边界设计为可注入、可单元测试的逻辑。

**Non-Goals:**

- 不添加操作系统资源管理器、Finder 或桌面环境的原生右键菜单。
- 不下载、安装、升级或配置 Codex 与 Claude CLI。
- 不在命令后来不可用时自动删除已经持久化的菜单项。
- 不根据菜单名称或近似命令推断用户自定义项的所有权；仅使用精确 `command` 字段避免重复入口。
- 不增加代理选择开关、专用图标或新的设置字段。

## Decisions

### 启动阶段使用当前进程命令环境检测

在 Wails `startup` 回调中调用独立的代理菜单同步逻辑。检测使用 Go 的命令查找语义分别解析 `codex` 和 `claude`，从而自然使用 Unix `PATH` 和 Windows `PATH`、`PATHEXT` 规则。查找函数通过依赖注入传入同步逻辑，单元测试无需依赖开发机是否真实安装代理。同步由仓储在同一变更锁内读取最新设置、合并并原子保存；导出的设置读取与保存等待启动同步结束，避免前端首次读取旧菜单或用旧快照覆盖并发设置。

备选方案是在用户配置 Shell 中运行 `command -v`、`Get-Command` 或 `where`。该方案会引入 Shell 类型判断、输出解析和启动时子进程，并可能弹出 Windows 控制台窗口，因此不采用。

### 使用稳定标识执行追加式合并

为两个自动项定义项目保留的稳定标识，例如 `auto.agent.codex` 与 `auto.agent.claude`。同步函数接收已有 `TaskMenuItems` 和检测结果，按固定候选顺序仅追加缺少稳定标识且命令可用的项。已有稳定标识意味着用户已经得到或修改了该项，系统保留其完整内容与位置。

除稳定标识外，启动合并还把命令型菜单中精确等于 `codex` 或 `claude` 的 `command` 字段视为用户已经配置对应入口；名称和参数不参与判断。这样可避免为已有自定义代理入口重复追加，同时不会因同名但执行其他命令的菜单误判。自动项继续使用现有 `command` 类型，因此现有设置界面、右键菜单和任务操作菜单无需新增数据模型分支。

### 在仓储根数据记录自动项删除选择

用户通过设置保存删除自动稳定 ID 时，仓储在同一变更锁内比较保存前后的菜单列表，将被删除的自动 ID 写入根数据的 `dismissedAgentTaskMenuItemIds`。该字段不属于公开 `Settings`，因此前端设置快照不会覆盖它，也不需要修改 Wails 绑定。

启动合并先检查删除记录；命中的候选永不自动恢复。删除普通自定义菜单不产生记录。当前不增加恢复开关，用户需要恢复时可以通过现有菜单编辑器手动新增命令。

### 仅在设置发生变化时持久化

同步函数返回新设置和变化标记。仓储只在实际追加至少一个菜单项时保存，使规范化和持久化数据继续作为唯一事实来源；重复启动不产生无意义写入。检测或同步失败不阻止 Wails 窗口启动，保存失败通过现有可用的应用错误发布方式报告，不能留下部分菜单更新。

不把检测结果保存在内存中，也不在 `GetSettings` 时临时拼接菜单，否则设置页面、命令执行和磁盘数据会形成多个事实来源。

### 自动项保存命令名称并复用配置 Shell

菜单项保存用户可理解且跨安装位置稳定的 `codex` 或 `claude` 命令名称，不持久化启动时解析到的绝对路径。绝对路径可能在升级、版本管理器切换或跨设备迁移后失效；启动检测的解析结果只用于判定命令当前是否存在。

Unix 与 Windows 的内嵌终端都通过共享的配置 Shell 命令构造器启动，覆盖 POSIX Shell、fish、cmd 与 PowerShell 的参数语义。Windows 带命令的 ConPTY 请求因此可执行 `.cmd` 包装文件并保持参数边界。实现不为 Codex、Claude 写专用分支；普通交互 Shell 和后台无窗口进程语义不得改变。

## Risks / Trade-offs

- [图形方式启动应用时的 `PATH` 可能少于用户交互 Shell] → 明确以应用启动进程可见环境为检测依据；用户仍可使用现有菜单设置手动添加命令。
- [用户删除自动项后不希望再次出现] → 仓储永久记录被删除的自动稳定 ID，后续启动跳过该候选；需要恢复时用户手动新增。
- [代理卸载后菜单项仍然存在] → 采用非破坏性的追加式同步，不自动删除持久化设置；执行时沿用现有“命令找不到”错误反馈。
- [Windows Shell 包装可能影响现有命令终端] → 将改动限制在带 `Command` 的 Windows ConPTY 分支，并为 PowerShell、cmd、直接可执行文件和 `.cmd` 包装形式增加回归测试。
- [启动保存失败导致本次没有自动菜单] → 保持原设置不变并报告错误，下一次启动仍可重试同步。
- [启动同步与前端设置访问竞态] → 仓储原子合并最新数据，并以启动就绪屏障阻止导出的设置读写抢先执行。

## Migration Plan

1. 新版本首次启动时读取现有设置并追加当前可检测到的自动菜单项。
2. 旧数据结构无需迁移；新增项使用现有 `TaskMenuItem` JSON 结构保存。
3. 回滚到旧版本时，这些项仍是合法的普通自定义命令菜单，可继续显示和执行。
4. 若需撤销自动补充逻辑，停止启动同步即可，不批量删除用户已经保存或修改的菜单项。
