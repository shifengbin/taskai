## Requirements
### Requirement: Release 提供可验证的更新清单

系统 MUST 在 tag 对应的 GitHub Release 中发布 `taskai-update.json`。清单 MUST 包含 schema 版本、目标语义版本、tag、该版本的 GitHub Release 页面，以及 Linux amd64 DEB、Windows amd64 NSIS 和 macOS universal DMG 的文件名、字节大小与 SHA-256。带预发布后缀的 tag 所创建的 GitHub Release MUST 标记为 Prerelease；Draft Release MUST NOT 成为更新来源。

#### Scenario: 正式版生成三端更新清单

- **WHEN** 三端发布任务成功汇总 `v1.2.3` 的 DEB、NSIS 和 DMG
- **THEN** Release 附带 schema 有效的 `taskai-update.json`，且三个资产条目的文件名、大小和 SHA-256 与实际产物一致

#### Scenario: 预发布 tag 标记为 Prerelease

- **WHEN** 发布工作流由 `v1.2.3-rc.1` tag 触发
- **THEN** GitHub Release 标记为 Prerelease，清单版本与 tag 均指向 `v1.2.3-rc.1`

#### Scenario: 产物缺失时不发布不完整清单

- **WHEN** 任一受支持平台的安装包缺失、版本非法或无法计算大小与 SHA-256
- **THEN** 发布任务失败，且不发布声称包含该安装包的不完整更新清单

### Requirement: 应用定期发现最高可用版本

系统 SHALL 在应用启动后异步检查一次官方 `shifengbin/taskai` 仓库的 GitHub Releases，并在应用继续运行期间每小时检查一次。系统 MUST 忽略 Draft、无效语义版本、不高于当前应用版本、清单无效或没有当前平台资产的 Release，并 MUST 在正式版和预发布版本中按语义版本选择最高可用版本。

#### Scenario: 启动后发现预发布版本

- **WHEN** 当前版本为 `v1.2.3-beta.1`，官方 Releases 中存在有效的 `v1.2.3-rc.1` 以及更旧正式版
- **THEN** 应用启动检查选择 `v1.2.3-rc.1` 为目标更新

#### Scenario: 正式版优先于同版本预发布

- **WHEN** 当前版本低于 `v1.2.3-rc.1`，且 `v1.2.3-rc.1` 与 `v1.2.3` 都具有有效的当前平台资产
- **THEN** 应用选择语义版本更高的 `v1.2.3`

#### Scenario: 忽略 Draft 和非法版本

- **WHEN** Release 列表只包含 Draft、无法解析的 tag 或不高于当前应用的版本
- **THEN** 应用保持无可用更新状态

#### Scenario: 当前平台没有匹配资产

- **WHEN** 较高版本的清单没有当前操作系统与架构对应的资产
- **THEN** 应用忽略该候选版本且不显示自动下载入口

#### Scenario: 每小时重新检查

- **WHEN** 启动检查完成且应用持续运行一个检查周期
- **THEN** 系统再次执行一次更新检查，并保证没有两个检查同时运行

#### Scenario: 检查失败后保持静默

- **WHEN** GitHub 查询超时、被限流或返回无效响应
- **THEN** 应用不显示下载失败提示、不影响任务工作台使用，并在下一个小时周期再次尝试

### Requirement: 更新入口展示稳定且可操作的状态

系统 SHALL 在“任务工作台”标题右侧显示紧凑且尺寸稳定的更新入口。无可用更新或仅自动检查失败时入口 MUST 隐藏；发现更新时入口 MUST 显示 `new` 并在辅助说明中包含目标版本；用户下载期间、下载失败和完成后 MUST 分别显示下载中、下载失败和已下载状态。

#### Scenario: 发现新版本后显示 new

- **WHEN** 更新服务发现当前平台可用的更高版本
- **THEN** 标题右侧出现 `new` 更新入口，悬浮说明包含目标版本

#### Scenario: 下载中禁止重复开始

- **WHEN** 用户点击 `new` 且安装包正在下载
- **THEN** 入口显示固定尺寸的下载中状态并禁止再次开始下载

#### Scenario: 下载完成后允许再次打开确认

- **WHEN** 下载校验成功后用户在安装确认中选择稍后
- **THEN** 入口显示已下载，且再次点击会重新打开该版本的安装确认

#### Scenario: 自动检查错误不显示失败入口

- **WHEN** 后台自动检查发生网络或服务错误
- **THEN** 更新入口不切换为下载失败，且界面不弹出下载失败对话框

### Requirement: 安装包下载必须完整校验

系统 MUST 将目标安装包下载到应用数据目录下独立的版本缓存。下载 MUST 先写入同目录临时文件并流式计算 SHA-256；只有实际字节数与清单大小一致且 SHA-256 匹配后，系统才能原子提交正式缓存文件并进入已下载状态。系统 MUST 限制同一时刻最多一个安装包下载。

#### Scenario: 下载并校验成功

- **WHEN** 用户开始下载且响应字节数和 SHA-256 均与清单一致
- **THEN** 系统原子提交安装包、移除临时文件、进入已下载状态并立即显示安装确认

#### Scenario: 响应中断或大小不符

- **WHEN** 下载请求中断或实际字节数与清单不一致
- **THEN** 系统删除临时文件、不产生可安装缓存并进入下载失败状态

#### Scenario: SHA-256 不匹配

- **WHEN** 下载内容的 SHA-256 与清单不一致
- **THEN** 系统删除临时文件、不启动安装程序并进入下载失败状态

#### Scenario: 拒绝并发下载

- **WHEN** 安装包下载尚未结束时再次收到开始下载请求
- **THEN** 系统不创建第二个下载或第二个缓存写入者

#### Scenario: 拒绝清单中的外部资产

- **WHEN** 清单的 tag、版本、Release 页面或资产名称不能与官方仓库同一 Release 的元数据对应
- **THEN** 系统拒绝下载该资产且不访问清单指向的任意外部下载地址

### Requirement: 已下载更新可安全恢复

系统 MUST 为已校验安装包持久化目标版本、平台、Release 页面、文件名、大小和 SHA-256 元数据，并在联网检查前完成缓存恢复。应用重启后 MUST 清理遗留临时文件和过期版本缓存，并对目标版本的缓存安装包重新校验大小与 SHA-256 后才恢复已下载状态。缓存版本不高于当前应用版本、平台不匹配或重新校验失败时，系统 MUST 删除该缓存且不得提供安装操作。

#### Scenario: 重启后恢复有效缓存

- **WHEN** 应用数据目录存在高于当前版本且大小与 SHA-256 均有效的目标安装包
- **THEN** 应用恢复已下载状态，用户无需再次下载即可打开安装确认

#### Scenario: 离线重启恢复有效缓存

- **WHEN** 应用在离线或 GitHub 不可用时重启，且存在元数据与安装包均有效的当前平台更新缓存
- **THEN** 应用在联网检查失败前恢复已下载状态，并保留该状态等待用户安装

#### Scenario: 重启后删除损坏缓存

- **WHEN** 缓存文件存在但重新计算的大小或 SHA-256 与清单不一致
- **THEN** 系统删除该缓存并恢复为可重新下载状态

#### Scenario: 清理临时与过期版本

- **WHEN** 应用启动时发现 `.part` 文件或不高于当前应用版本的更新目录
- **THEN** 系统清理这些文件，且不会把它们显示为已下载更新

### Requirement: 下载失败支持重试和手动下载

用户主动下载发生网络错误、响应错误或完整性校验失败时，系统 SHALL 将入口切换为下载失败并显示对话框，提供重新下载、手动下载和取消。手动下载 MUST 打开当前目标版本的官方 GitHub Release 页面，而不是通用 Latest 地址；打开页面失败 MUST 显示错误且保持现有更新状态。

#### Scenario: 下载失败后重新下载

- **WHEN** 首次安装包下载失败且用户选择重新下载
- **THEN** 系统为同一目标版本发起新的单次下载并重新执行完整校验

#### Scenario: 下载失败后手动下载

- **WHEN** 下载失败后用户选择手动下载
- **THEN** 系统使用默认浏览器打开该目标版本的官方 GitHub Release 页面

#### Scenario: 打开手动下载页失败

- **WHEN** 系统无法打开目标 Release 页面
- **THEN** 应用显示普通错误提示且保留下载失败或已下载状态

### Requirement: 安装遵守平台启动和现有退出语义

系统 SHALL 使用当前平台的安装方式打开已校验安装包：Windows 启动 NSIS 且不额外显示控制台窗口，macOS 通过系统 `open` 打开 DMG，Linux 通过 `xdg-open` 打开 DEB。系统 MUST 先成功启动安装程序，之后才能调用现有 `PrepareQuit` 关闭终端并退出 TaskAI；启动失败时 MUST 保持应用运行并提供重试安装和手动下载。

#### Scenario: 无执行中任务时安装

- **WHEN** 用户确认安装且没有执行中任务
- **THEN** 系统先启动当前平台安装程序，成功后关闭终端并退出 TaskAI

#### Scenario: 有执行中任务时确认安装

- **WHEN** 用户确认安装但仍有执行中任务
- **THEN** 系统显示现有退出确认语义，说明只关闭终端、不改变任务状态或删除工作目录，并提供“关闭终端并安装”动作

#### Scenario: 取消执行中任务确认

- **WHEN** 用户在执行中任务安装确认中选择取消
- **THEN** 系统不启动安装程序、不关闭终端、不退出，并保持已下载状态

#### Scenario: 安装程序启动失败

- **WHEN** 平台安装程序或系统打开命令无法启动
- **THEN** 系统不调用 `PrepareQuit`、保持 TaskAI 运行，并提供重试安装和手动下载

#### Scenario: Windows 安装不弹出控制台窗口

- **WHEN** Windows 用户确认启动已下载的 NSIS 安装程序
- **THEN** 系统使用后台进程配置启动安装程序，不额外弹出控制台窗口

### Requirement: 更新状态通过 Wails 可靠同步

系统 SHALL 通过 Wails 查询接口返回当前更新状态，并在状态变化时发布事件。前端 MUST 在挂载时发起当前状态查询、立即订阅变化并在首个查询完成后再次读取当前状态，且 MUST 防止旧查询快照覆盖较新的事件；卸载时 MUST 移除事件订阅。该同步过程既要正确显示发生在前端订阅之前的启动检查结果，也不得永久丢失查询与订阅建立之间发生的状态变化。

#### Scenario: 前端恢复启动早期状态

- **WHEN** 启动检查在前端事件订阅建立前已经发现更新
- **THEN** 前端通过初始状态查询显示该更新，不要求等待下一次事件或下一小时检查

#### Scenario: 查询与订阅之间发生状态变化

- **WHEN** 前端首次查询期间更新状态发生变化
- **THEN** 前端通过事件或订阅后的再次查询显示最新状态，旧查询结果不得覆盖最新状态

#### Scenario: 状态变化实时更新入口

- **WHEN** 后端状态从可用依次变为下载中和已下载
- **THEN** 前端通过状态事件依次更新入口，且不创建重复订阅

#### Scenario: 前端卸载清理订阅

- **WHEN** 任务工作台前端卸载
- **THEN** 系统移除更新状态事件监听，后续状态变化不会调用已卸载组件

### Requirement: 集成测试更新源与生产源隔离

系统 MUST 仅在带 `updater_integration` 构建标签的开发构建中允许 `TASKAI_UPDATE_TEST_URL` 指向本地更新测试服务器，并 MUST 在该模式中替换真实安装程序启动。未带该标签的生产构建 MUST 固定使用官方仓库且忽略测试更新源变量。

#### Scenario: 集成构建使用本地更新服务

- **WHEN** 开发者以 `updater_integration` 标签和 `TASKAI_UPDATE_TEST_URL` 启动 `wails dev`
- **THEN** 更新检查与下载访问本地测试服务器，并且安装确认不启动真实系统安装程序

#### Scenario: 生产构建拒绝测试源覆盖

- **WHEN** 未带 `updater_integration` 标签的构建环境设置了 `TASKAI_UPDATE_TEST_URL`
- **THEN** 应用忽略该变量并继续只使用固定的官方仓库更新源

#### Scenario: 本地完整交互验证

- **WHEN** 测试服务器提供更高版本且第一次下载失败、第二次返回有效安装包
- **THEN** 浏览器测试可依次观察 `new`、下载中、下载失败、重新下载、安装确认、稍后安装和已下载恢复状态
